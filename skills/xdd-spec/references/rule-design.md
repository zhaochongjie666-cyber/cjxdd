# 规则设计方法 — 怎么把意图拆成 RXX 规则

> 本文件是 `xdd-spec` 的深度参考。SKILL.md 讲"每条规则 = RXX + Feature"，这里讲**怎么拆**：规则粒度多大、怎么从 Feature 倒推规则、异常路径怎么穷举、Scenario 怎么写具体可验。
> 配合 `xdd-gherkin-plus`（Gherkin 语法）—— 本文件讲**设计判断**，那边讲**语法格式**。

---

## 1. 规则是什么（边界）

规则（RXX）= **一条可验收的业务约束**。不是功能点，不是用户故事，是"系统在 X 情况下必须 Y"的断言。

| 是规则 ✅ | 不是规则 ❌ |
|----------|------------|
| 未登录用户不能创建任务（权限约束）| 任务管理（功能点，太泛）|
| 短码 7 天未访问自动过期（业务约束）| 短码功能（功能点）|
| 订单金额不能为负（数据约束）| 订单系统（功能点）|
| 管理员可查看所有用户数据（权限）| 用户管理（功能点）|

**判断**：能写成"Given...When...Then..."的可验收断言 = 规则。只是"做个 X 功能" = 还没拆成规则。

---

## 2. 规则粒度（最常见的错误）

**一条规则 = 一个可独立验收的业务约束**。粒度判断：

| 太粗（要拆）| 合适 | 太细（要合并）|
|------------|------|--------------|
| R01 用户管理 | R01 未登录不能创建任务 | R01 检查 token 是否存在 |
| R01 登录功能 | R02 密码错 5 次锁账户 | R02 查询用户表 |
| | R03 token 15 分钟过期 | R03 返回 401 状态码 |

**判定法**：
- 一条规则能不能用**一句话**说清约束？说不清 = 太粗，拆。
- 这条规则失败了，要不要**单独验收**？不要 = 太细，合到上层规则。
- 两条规则是**同一个约束的正反两面**吗？是 → 合并（"未登录不能创建" + "已登录能创建" 是一条权限规则的正反，合成一条带异常路径的规则，不要拆两条）。

> **常见错误**：把"正向 + 异常"拆成多条规则。例：登录成功 R01、密码错 R02、账户锁定 R03、token 过期 R04 —— 其实是**一条登录规则 + 4 个 Scenario**。规则粒度按"业务约束"切，不按"代码分支"切。

---

## 3. 从意图拆规则的 4 步

### 第 1 步：从 design.md 提取约束种子

brainstorm 的 design.md 里（见字段映射）：
- **Selected**（做什么）→ 正向约束种子
- **Out of Scope**（不做什么）→ 边界约束种子
- **Assumptions**（假设）→ 前置约束种子
- **Open Questions**（待定）→ 标 TODO，不编规则

### 第 2 步：每条约束问"什么时候不满足"

正向约束必带异常路径。对"未登录不能创建任务"问：
- 没登录 → 拒绝（异常 1）
- 登录了但没权限 → 拒绝（异常 2）
- 登录了有权限但参数非法 → 拒绝（异常 3）
- 都满足 → 允许（正向）

**每条规则的异常路径，穷举问这几个维度**：

| 维度 | 问 | 例子 |
|------|----|------|
| 权限 | 谁不该能做？ | 未登录 / 无权限角色 |
| 数据 | 输入什么会非法？ | 负数 / 超长 / 格式错 / 重复 |
| 状态 | 什么状态下不能做？ | 已删除 / 已锁定 / 已完成 |
| 资源 | 资源不存在/超限？ | 404 / 配额耗尽 / 不属于你 |
| 并发 | 同时操作呢？ | 重复提交 / 并发改同一资源 |
| 外部 | 依赖挂了？ | 第三方超时 / 存储失败 |

### 第 3 步：每条规则写成一个 Feature

一条规则 = 一个 Feature 文件。Feature 含 Background + 正向 Scenario + 异常 Scenario（用 Scenario Outline 覆盖同类异常）。详见 `xdd-gherkin-plus`。

### 第 4 步：交叉检查（防漏）

- 每条 RXX 有 ≥1 正向 + ≥1 异常 Scenario？没有异常路径的规则多半漏想了。
- design.md 的每个 Out of Scope 有对应"不允许"的规则或 Scenario？
- spec _landscape.md 的业务线清单和规则归属一致？

---

## 4. Scenario 写具体（不是写笼统）

验收的价值在**具体**。笼统的 Then 测不出 bug。

| 笼统（没用）| 具体（可验）|
|------------|------------|
| Then 返回错误 | Then 响应状态码 401，body 含 `{"code":"UNAUTHORIZED"}` |
| Then 创建成功 | Then 响应 201，body 含 `taskId`，数据库 `tasks` 表多一条 `status=pending` |
| Then 显示提示 | Then 页面顶部显示红色提示"余额不足"，3 秒后消失 |
| Then 不能操作 | Then 创建按钮 disabled，hover 显示"余额不足无法创建" |

**具体化三要素**：① 状态码/字段名（接口层）② 数据库/状态变化（持久层）③ 用户可见反馈（UI 层）。每条 Then 至少落到一层，最好多层。

> Scenario Outline + Examples 覆盖同类：一种异常（如"非法输入"）用 Outline 列多种非法值，不写 10 个雷同 Scenario。详见 `xdd-gherkin-plus`。

---

## 5. 跨业务线规则归属

多业务线项目，规则归哪条 BXX？
- 规则**只涉及一条业务线** → 归该 BXX 的 rules.md（`B01-R01`）
- 规则**跨业务线**（如"订单触发通知"）→ 主操作方（order）出规则，通知方（notify）订阅；或在 `cross-cutting/` 下单独列
- **通用基础能力**（auth/storage）→ 别给它编业务 RXX（那是基础模块，用现成方案，见 architecture §13）

---

## 6. 自检（spec 规则设计质量）

```
□ 每条 RXX 是"可验收的业务约束"，不是功能点？（能写成 Given/When/Then）
□ 粒度合适？一句话能说清 + 需单独验收？（不粗不细）
□ 没把"正向+异常"拆成多条规则？（异常是 Scenario 不是 RXX）
□ 每条规则穷举了异常路径（权限/数据/状态/资源/并发/外部 6 维度）？
□ Then 具体可验（状态码/字段/数据变化/UI 反馈），不是笼统"返回错误"？
□ design.md 的 Out of Scope 都有对应"不允许"的规则或 Scenario？
```
