# 代码品味标准

代码品味 = 读代码的人不需要问原作者就能理解。命名精确、结构清晰、不多不少。

## 致命三检（代码版）

1. **命名检验** — 读一个函数名/类名，不看实现，能猜出它做什么吗？不能 → 命名不够精确。
2. **减法检验** — 删掉一个类/方法/参数/if 分支，系统行为是否不变？不变 → 它是多余的。
3. **可读检验** — 给不熟悉项目的新人看，5 分钟能理解这个模块？不能 → 结构或命名有问题。

## Code Smell 清单（REFACTOR 阶段必检）

| Smell | 信号 | 处理 |
|-------|------|------|
| **函数过长** | > 20 行 | 拆成多个小函数 |
| **参数过多** | > 3 个 | 用值对象/配置对象包装 |
| **嵌套过深** | if/for 嵌套 > 2 层 | 提前 return / 提炼方法 |
| **重复代码** | 相同逻辑 ≥ 3 处 | 提取公共方法/类 |
| **注释解释"怎么做"** | `// 遍历列表并求和` | 删注释，改命名（`sumItems` 比注释清楚） |
| **catch 空块** | `try {...} catch {}` | 要么处理，要么让异常传播，不能空吞 |
| **魔法数字/字符串** | `if status == 3` | 提取为常量 `STATUS_APPROVED = 3` |
| **过长参数链** | `a.b.c.d()` | 违反 Demeter 法则，用方法提取 |
| **布尔参数** | `process(True)` | 拆成两个方法或枚举传参 |
| **返回 null** | `return null` 导致调用方 null check | 用 Optional / 空对象模式 / Result 类型 |

一次重构只消除 1-2 个 Smell。一口气全改光容易引入 bug。

## SOLID 速查（L3 契约层参考）

| 原则 | 一句话 | 违例信号 |
|------|--------|---------|
| S（单一职责） | 一个类只有一个变化的理由 | 类名含"and"（`UserManagerAndExporter`） |
| O（开闭） | 加功能不改已有代码，通过扩展 | 加功能时到处改 if-else |
| L（里氏替换） | 子类能替换父类，调用方无感知 | 子类 override 方法后抛不支持异常 |
| I（接口隔离） | 接口要小，不强迫实现不需要的方法 | 接口中有 3 个方法 2 个用不上 |
| D（依赖反转） | 依赖抽象，不依赖具体实现 | new() 具体类在业务代码中直接出现 |

## 错误处理原则

- **不吞异常**：catch 空块 = 品味缺口。要么处理（记日志 + 返回友好错误），要么传播（不 catch）。
- **错误信息写给人看**：`"用户不存在"` 优于 `"ER-001"` 优于 `空`。错误信息也是一种 UI。
- **失败可发现、可解释、可恢复、可追责**：与 Harness 计划 P0 测试对齐。
- **边界校验在入口做**：API 层/公共方法入口校验参数，内部方法假设参数已合法（防御式编程）。
- **异常不是业务流程**：不要用 try-catch 控制业务逻辑流程。用模式匹配/状态机/Result 类型替代。

## 语言惯用法

框架语言直接引用该语言的官方风格指南即可，本文件不做穷举。以下是最常见的三类陷阱：

| 语言 | 推荐 | 不推荐 |
|------|------|--------|
| Python | property/dataclass/classmethod | Java 风格 getter/setter |
| TypeScript | type guard / discriminated union / interface | any / ! 非空断言 |
| Go | error 作为返回值 / interface 组合 | panic 作为业务异常 / 大 interface |
