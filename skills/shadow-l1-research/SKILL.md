# Shadow·DDD+EDD+IDDD — 意图驱动 + 领域驱动 + 事件驱动调研

## 角色

帮你在动手写代码之前想清楚**为什么要做**、业务领域和事件驱动架构。IDDD + DDD + EDD 是**思考工具**，不是文档填空：

| 思考工具 | 帮你回答 |
|---------|---------|
| **意图定义（IDDD）** | 为什么做这个？成功标准是什么？需求变更时如何追溯？ |
| **用户理解** | 谁会用？怎么用？谁会误用？极端场景怎么办？ |
| 业务全景 | 有哪些业务线？业务线间如何依赖？全局事件流是什么？ |
| 统一语言 | 业务方和开发说的是一回事吗？ |
| 事件风暴 | 领域里到底发生了什么？事件之间如何流转？ |
| 限界上下文 | 边界在哪？哪个是核心？ |

**IDDD（意图驱动开发）**：在业务调研的第一步就定义项目意图。后续每条规则、每个 API 端点、每个技术选型都标注"为什么"。需求变更时，追溯到原始意图评估偏离。

**EDD（事件驱动开发）显式化**：事件风暴不只是列出事件，还要决定事件如何传递——进程内事件总线（模块化单体）还是消息队列（微服务/分布式）。这个决策影响 L1.5 Architecture 的技术栈和 L3/L5 的实现方式。

**业务全景 vs 业务线**：
- **意图定义（intent.md）**：项目级意图，所有业务线共享
- **业务全景（business-landscape.md）**：全局视角，列出所有业务线及依赖关系，架构师掌握全局的入口
- **项目流程总图（project.flow.mermaid）**：项目级唯一业务流程总图，承载所有业务线的 BXX 泳道和跨域流转
- **业务线（BXX-{slug}/）**：单条业务的详细调研，每条业务线有独立的 research.md/spec.md/wire 产物，不再维护独立 flow 文件

## 怎么做

### 0. 从 L0 笔记本收敛

**前置**：L0 发散笔记本（`.shadow/L0-research/`）已完成。

**L0 文件 → L1 提取映射**：

| L0 文件 | 提取什么 | 写入哪个 L1 产出 |
|---------|---------|-----------------|
| `01-industry-notes.md` | 行业背景、公认模式、行业基线 | intent.md §业务背景 + research.md §业务背景 |
| `02-competitor-analysis.md` | 竞品功能对比、差异化机会 | intent.md §成功标准（对标竞品） |
| `03-user-personas.md` | 6 维画像发散（原始） | intent.md §用户画像 → research.md §统一语言 |
| `04-user-journeys.md` | 5 层旅程穷举（原始） | intent.md §用户旅程 → research.md §旅程图 |
| `05-tech-research.md` | 技术路线利弊、开源项目参考 | research.md §技术选型 + §外部调研 |
| `06-events-brainstorm.md` | 事件风暴发散（原始） | research.md §事件风暴 |
| `07-external-references.md` | 外部来源链接和要点 | research.md §外部调研 §来源表 |

按上表顺序逐文件提取，确保每个 L0 文件的关键发现都被吸收到对应的 L1 产出中。

**收敛原则**：
- 从 L0 笔记中提取关键结论，丢弃中间过程
- 收敛后的产出必须精简但全面——coder 看到这些产出后不需要看 L0 笔记
- 画像合并到区分度检验不通过为止（如果 `.shadow/scale.md` 存在，按 `persona_max` 参数取上限；否则 ≤ 8 个）
- 旅程合并相似路径（≤ 画像数 × 5 条）
- 事件合并同义词
- 方案从 N 个收敛到 2 个

**收敛检查**：
1. 删掉 30% 内容后，下游（Flow/Spec/Wire/Harness）是否仍能开工？
2. L0 笔记中的关键发现是否全部被提取到 L1 产出中？
3. 有没有 L0 笔记中记录但 L1 产出中遗漏的风险或约束？

### 0.1 意图定义 — 为什么做这个？（IDDD）

**时机**：在业务全景之前，作为整个项目的第一步。

**核心问题**：
- 做这个项目的**根本原因**是什么？（不是"做什么"，而是"为什么"）
- **成功标准**是什么？如何量化？（"标注效率提升 40%"比"做一个标注平台"更精确）
- 如果需求变更，如何判断是**正常演进**还是**偏离意图**？

**产出**：`.shadow/L1-business/intent.md`

```markdown
# 项目意图定义

## 项目背景
原始需求来源、业务痛点、为什么要做这个。

## 核心意图（一句话）
用一句话描述项目的核心目的。

## 成功标准（可量化）
| 指标 | 当前值 | 目标值 | 度量方式 |
|------|--------|--------|---------|
| 标注效率 | 人工 2h/百条 | < 30min/百条 | 平均标注时间 |
| 质检通过率 | 70% | > 95% | 一致性分数 |

## 用户画像（收敛后，如果 `.shadow/scale.md` 存在按 `persona_max` 参数取上限，否则 ≤ 8 个）

从 L0 笔记中收敛的用户画像。每个画像必须有一行核心区分度。

| 画像ID | 角色 | 核心区分度 | 预期路径数 |
|--------|------|-----------|-----------|
| P-01 | {角色1} | {一句话区分度} | ~8 |
| P-02 | {角色2} | {一句话区分度} | ~6 |
| ... | ... | ... | ... |

**区分度检验**：把每个画像的核心行为列出来，如果两个画像的操作路径高度重合 → 合并。

## 用户旅程（收敛后）

从 L0 笔记中收敛的旅程。只保留关键旅程（每个画像主线 1 条 + 关键分支/异常 ≤ 5 条）。

| 画像 | 主线 | 分支 | 迂回 | 意外 | 探索 | 总计 | 涉及业务线 |
|------|------|------|------|------|------|------|-----------|
| P-01 | 1 | 4 | 3 | 2 | 3 | 13 | B01,B02 |
| ... | ... | ... | ... | ... | ... | ... | ... |

**旅程完成标准**：总旅程数 ≥ 画像数 × 5。每个画像至少覆盖主线+分支+意外各 1 条。

## 意图约束（不可妥协的底线）
- 数据安全：标注数据不能泄露给未授权人员
- 多模态支持：必须同时支持文本、图片、音频标注

## 变更追溯基准
后续需求变更时，必须回答：
1. 原始意图是什么？（来自本文档）
2. 变更是正常演进还是偏离？
3. 偏离的话，是否需要重新评估项目方向？
```

**传导方式**：
- `intent.md` → spec.md 每条规则标注 `@intent`（为什么需要这条规则）
- `intent.md` → architecture.md 技术选型标注 `@intent`（为什么选 React 而不是 Vue）
- `intent.md` → plan.json 每个任务标注 `intent`（为什么需要这个聚合）
- `intent.md 用户画像` → L1 Flow（流程覆盖旅程）→ L1 Spec（规则覆盖旅程）→ L1 Wire（页面交互支撑旅程）→ L2 E2E（消费画像 + 独立发散校验）→ L5 Harness（Harness 计划覆盖旅程）
- 需求变更时追溯 `intent.md` 评估偏离

### 0.2 旅程图格式（收敛后）

从 L0 笔记中收敛的关键旅程，使用业务场景语言记录：

```markdown
## 旅程图：P-XX → <目标> [J-L1-XX]

| 属性 | 值 |
|------|-----|
| 画像 | P-XX: <名称> |
| 旅程类型 | 主线/分支/迂回/意外/探索 |
| 触发条件 | <什么情况下会走这条路径> |
| 涉及业务线 | <BXX 列表> |

| 步骤 | 用户操作（业务场景语言） | 用户看到的场景 | 可能分支 |
|------|----------------------|-------------|---------|
| 1 | ... | ... | ... |
```

旅程图要求（从 L0 发散笔记收敛时遵循）：
- **用户操作列**：用业务动作描述，不写 URL/组件/技术术语
- **用户看到的场景列**：用自然语言描述用户看到的界面场景
- **场景命名一致性**：相同界面使用相同场景名称
- **场景粒度**：精确到"一个页面/弹窗/抽屉/状态变体"
- **可能分支列**：包括成功路径和失败路径

### 品味引导：有温度的用户描绘

**画像不是标签堆砌。** 以下两组画像，读者感知截然不同：

```
无品味（标签堆砌）:
  P-01 | 标注员 | 熟练 | 高频 — 一个没有面孔的统计条目

有品味（有人物感）:
  P-01 | 标注员 | 熟练 | "每天同时开 3 个浏览器标签页做标注，
        鼠标从不在按钮上悬停超过 0.5 秒，快捷键比菜单更熟练。
        他知道每个按钮点下去会发生什么——厌恶意外。"
```

**区分度检验**：把每个画像的核心行为列出来，如果两个画像的操作路径高度重合 → 合并。不要为了凑 5 个画像而把同一个人拆成两个——凑出来的没有品味可言。

**旅程不是模板填空。** "用户登录→选择任务→标注→提交"是一条正确的旅程，但毫无品味。它只描述了功能，没有描述人：

```
无品味（功能清单）:
  步骤 1: 登录系统
  步骤 2: 选择任务
  步骤 3: 进行标注
  步骤 4: 提交标注

有品味（有心流）:
  步骤 1: 打开浏览器，书签栏第一行点击"标注平台"，看到登录页光标已在用户名框闪烁
  步骤 2: 输入账号后按 Tab 跳到密码框（不是鼠标点的——因为每天做 50 次，肌肉记忆了）
  步骤 3: 回车登录，页面自动跳转到任务列表，直接点击第一个"待处理"任务
  ...
```

**共性情绪的力量**：所有用户在某个时刻共享焦虑——害怕数据丢失、害怕操作不可逆、等待时的焦躁。把这些情绪写进"用户看到的场景"列：

```
无情绪:
  场景: 提交确认弹窗

有情绪:
  场景: 提交确认弹窗，底部有"取消"和"确认"两个按钮，
        红色按钮上写着"确认提交，进入审核后不可修改"
```

用户在读到后者时能"感觉到"那个场景。这才是好的用户描绘。

### 1. 业务全景 — 架构师的全局视图（新增）

**时机**：在开始各业务线详细调研前，先画出业务全景。

**产出**：`.shadow/L1-business/business-landscape.md`

#### 0.1 业务线清单

列出所有业务线，每条业务线标注：

| 维度 | 说明 |
|------|------|
| **业务线编号** | B01, B02, B03... |
| **slug** | 业务线英文名，小写连字符。一旦确定，全链路不可变。用作目录名、规则 ID 前缀、文件路径 |
| **业务线名称** | 采集打点、用户管理、标注... |
| **核心流程** | 一句话描述主流程 |
| **域类型** | Core（核心）/ Supporting（支撑）/ Generic（通用） |
| **依赖** | 依赖哪些其他业务线？被哪些业务线依赖？ |

**slug 规则**：
- 格式：小写英文字母 + 连字符，如 `collection`、`annotation`、`simulation`
- 来自业务线的核心域名词，简短且唯一
- 用途：`BXX-{slug}` 作为目录名（如 `.shadow/L1-business/B01-collection/`）、规则 ID 前缀（如 `collection-R01`）、全链路所有文件路径
- 确定后不可修改——下游 Flow、Spec、Wire、L1.5、L5 Plan、L5 Impl、L6 全部依赖此值

**示例**：
```markdown
## 业务线清单

| 编号 | slug | 名称 | 核心流程 | 域类型 | 依赖 |
|------|------|------|---------|--------|------|
| B01 | collection | 采集打点 | 创建任务→外场采集→打点记录→上传数据 | Core | — |
| B02 | annotation | 标注 | 打开任务→创建标注→提交质检→通过/驳回返工 | Core | B01(collection) |
| B03 | simulation | 仿真播放 | 选择场景→播放回放→标记问题→导出报告 | Supporting | B01(collection), B02(annotation) |
```

#### 0.2 业务线间依赖关系

画出业务线间的依赖方向：

```
B01(collection) ──(采集数据)──→ B02(annotation)
B01(collection) ──(采集数据)──→ B03(simulation)
B02(annotation) ──(标注结果)──→ B03(simulation)
```

**依赖类型**：
- **强依赖**：没有上游业务线，下游业务线无法运行（如 B01 依赖 B02 鉴权）
- **弱依赖**：下游业务线可以独立运行，但需要上游数据（如 B03 依赖 B01 数据）
- **双向依赖**：两个业务线互相依赖（需要警惕，可能边界划分不清）

#### 0.3 全局事件流

画出跨业务线的领域事件流转：

```
B01: CollectionStarted → B01: WaypointRecorded → B01: CollectionFinished → B01: DataAvailable
B02: AnnotationCreated → B02: AnnotationSubmitted → B02: ReviewPassed / B02: ReviewRejected
B03: SimulationStarted → B03: IssueMarked → B03: ReportExported
```

**关键**：标注每个事件属于哪个业务线，事件如何跨业务线传递。

#### 0.4 核心/支撑/通用域划分

| 类型 | 说明 | 开发策略 |
|------|------|---------|
| **Core Domain** | 核心业务，差异化竞争力 | 投入最多资源，自己做 |
| **Supporting** | 支撑核心业务 | 可以做，但可以简化 |
| **Generic** | 通用能力 | 外购/复用，不重复造轮子 |

列出所有核心业务术语，每个问三个问题：
- 这个词是什么意思？（定义）
- 谁会用这个词？（角色）

如果不同上下文里同一个词意思不同，必须分开列。

### 3. 事件风暴 — 发生了什么 + EDD 架构决策

#### 3.1 列出领域事件

用过去时态动词列出领域里发生的重要事件（OrderPlaced、PaymentFailed...）。

每个事件问：
- 什么触发了它？（命令/操作）
- 谁干的？（角色）
- 它改变了什么？（聚合状态变化）
- 谁需要知道？（其他上下文）
- **事件接收方在同一个进程还是不同进程？**（EDD 关键问题）

**关键原则**：事件是业务关心的，不是技术关心的。不要列技术事件。

#### 3.2 事件分类（EDD 准备）

把事件按**传递范围**分类：

| 类型 | 范围 | 传递方式 | 示例 |
|------|------|---------|------|
| **进程内事件** | 同一上下文内，聚合间协调 | EventBus（asyncio/观察者模式） | AnnotationSubmitted → ReviewRequested（同进程触发质检） |
| **跨上下文事件** | 不同限界上下文间，同一进程 | EventBus + 防腐层适配 | OrderPlaced → InventoryReserved（单体内部上下文协调） |
| **跨进程事件** | 不同服务实例，需要持久化 | Kafka/RabbitMQ/SQS | OrderPlaced → PaymentService（微服务间通信） |
| **外部系统事件** | 第三方系统，需要可靠投递 | Kafka + 死信队列 + 重试 | OrderShipped → 物流系统通知 |

#### 3.3 EDD 架构决策（显式选择）

根据事件分类，做出 EDD 架构决策：

**决策 1：事件传递基础设施**

| 方案 | 适用场景 | 优点 | 缺点 |
|------|---------|------|------|
| **进程内 EventBus** | 模块化单体、上下文间强耦合、实时性要求高 | 零延迟、零运维成本、调试简单 | 服务重启丢失未消费事件、无法水平扩展 |
| **消息队列（Kafka/RabbitMQ）** | 微服务、跨进程通信、需要事件持久化 | 可靠投递、支持重试、支持多消费者 | 运维复杂、延迟增加、调试困难 |

**决策问自己**：
- 事件丢失会影响业务吗？（订单支付失败事件不能丢）
- 事件消费者需要独立部署吗？（质检服务可能独立扩容）
- 当前团队规模能运维消息队列吗？（单体阶段用 EventBus，后期升级）

**决策输出**（写入 research.md）：
```
EDD 架构决策:
  - 进程内事件: AnnotationSubmitted → ReviewRequested（同进程触发质检）
  - 跨上下文事件: OrderPlaced → InventoryReserved（单体内部 EventBus）
  - 跨进程事件: 无（当前阶段单体架构，后期可升级 Kafka）
  - 外部系统事件: OrderShipped → 物流系统（预留 Kafka 接口，当前用 HTTP 回调）

  基础设施选择: 进程内 EventBus（asyncio），接口抽象保证后期可替换为 Kafka
```

#### 3.4 事件契约定义（预留给 L1.5 event-contract.md）

每个事件简要定义载荷结构（不重复定义，预留给 L1.5 Architecture）：

```

  - taskId: UUID
```

### 4. 限界上下文 — 边界在哪

划分子域：
- **Core Domain**：核心业务，差异化竞争力（自己做）
- **Supporting**：支撑核心业务（自己做但可以简化）
- **Generic**：通用能力（外购/复用）

划完后标出上下文之间的关系（上下游/共享内核/防腐层）。

**EDD 视角加强**：上下文间关系决定了事件传递方式：
- **上下游关系**：上游发布事件，下游订阅（跨上下文事件）
- **共享内核**：共享领域模型，不需要事件传递（直接调用）
- **防腐层（ACL）**：外部系统事件需要适配器转换

### 5. 外部调研 — 不闭门造车（强制步骤）

**时机**：在统一语言、事件风暴、限界上下文完成后，方案选型之前。

**核心问题**：别人怎么做的？有没有现成的最佳实践、开源方案、社区经验可以借鉴？

调研不充分 → 方案选型凭感觉 → 技术债从 L1 就埋下。必须通过外部调研找到**至少 3 个不同方向的参考来源**。

#### 5.1 调研方向（至少覆盖 3 个）

| 方向 | 调研目标 | 关键词示例 |
|------|---------|-----------|
| **行业最佳实践** | 该领域的公认设计模式、架构范式、流程标准 | `{domain} best practices`, `{domain} architecture patterns`, `{domain} design guide` |
| **开源项目参考** | GitHub 上同类型项目的架构、功能划分、技术选型 | `{domain} open source`, `github {domain} platform`, `{domain} similar project` |
| **社区推荐与讨论** | 技术社区、博客、论坛中的经验总结、踩坑记录 | `{domain} reddit`, `{domain} stack overflow`, `{domain} lessons learned`, `{technology} production experience` |
| **竞品/产品分析** | 市面上同类产品的功能列表、用户体验、差异化 | `{domain} product comparison`, `{domain} SaaS review`, `{competitor} features` |

#### 5.2 调研方法

1. **Web Search**：用 `MiniMax_web_search` 搜索上述关键词，每个方向至少搜索 1 次。
2. **Web Fetch**：对搜索结果中最相关的 2-3 篇文章，用 `webfetch` 获取详细内容。
3. **开源项目分析**：搜索 GitHub 上 star 数最高的同类型项目，分析其 README、架构文档、功能列表。
4. **经验提取**：从调研结果中提取可复用的设计模式、已知陷阱、推荐方案。

#### 5.4 调研与方案选型的关系

## 约束

- **L0 发散是前置条件**：L1 Research 开始前，L0 发散笔记本应已完成（`.shadow/L0-research/` 目录存在且有内容）
- **收敛是强制步骤**：从 L0 笔记中提取关键结论，丢弃中间过程，产出精简但全面的 L1 文档
- **收敛后画像 ≤ 8 个**（合并到区分度检验不通过为止）
- **收敛后旅程 ≥ 画像数 × 5**（关键旅程，不是全量旅程）
- **旅程描述使用业务场景语言**：不涉及 URL/组件/data-page/Playwright 等技术实现细节
- **外部调研结论必须有**：来源表 + 可借鉴模式 + 已知陷阱 + 技术选型参考（从 L0 笔记中收敛）
- **方案选型必须引用外部来源**：每个候选方案至少引用 1 个外部来源，没有调研支撑的方案不可接受
- 术语一旦定义，后续所有层必须保持一致使用
- 领域事件必须传导到 project.flow.mermaid 和 spec.md
- **EDD 架构决策必须显式写出**（进程内 EventBus / Kafka / 混合）
- **EDD 事件契约必须独立产出**（event-contract.md，不被隐式散射）
- **事件分类必须标注**（进程内/跨上下文/跨进程/外部系统）
- 限界上下文必须传导到 architecture.md
- 业务线间依赖必须传导到 business-landscape.md
- **每条 spec 规则必须标注 @intent**（为什么需要这条规则）
- **需求变更时必须追溯 intent.md**，评估偏离程度
- 如果调研完后你还觉得"不确定"，那是正常的。标出来，让下游知道风险
