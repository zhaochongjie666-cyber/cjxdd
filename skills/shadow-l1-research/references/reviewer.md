# L1 Reviewer — 攻击式审查 L1 业务设计质量

**输入:** L1 全套产出（research.md + project.flow.mermaid + wire 产物 + spec.md）

**触发时机:** L1 双轨 Gate 的第二轨（语义审查）

**审查目标：严重度加权总分 ≥6（阻塞=3,高=2,中=1,低=0），且阻塞+高已清零。**

### Todolist Checklist — 攻击方法

| # | 检查项 | 攻击方法 | 优先级 |
|---|--------|---------|--------|
| 1 | spec 自洽性 | 列出所有规则 ID，逐条检查"可观测状态"中是否有对应变化。列出所有角色，检查 flow 是否出现。检查约束是否被规则违反。 | high |
| 2 | flow 完整性 | 从 spec 每条规则追踪 flow 路径。检查入口明确性（触发来源）+ 交付物（resultNode）。对比 spec 异常流程和 flow 异常分支。 | high |
| 3 | 验收路径可走通 | 逐段模拟用户操作：每步入口/点击/结果是否明确？步骤是否跳跃？预期结果是否具体可观察？ | high |
| 4 | wire 业务化 | 区域名称是否用业务术语？有无无关通用组件？对比 flow 交互节点：wire 是否覆盖所有用户可见交互？每个交互元素是否有 `data-node="BXX-NYY"`？每个 flow 交互节点是否都有 wire 元素对应？（无 wire 则 N/A） | medium |
| 5 | 风险覆盖 | research.md 是否识别关键技术风险？每个风险有缓解策略？有无显而易见但未提的风险？ | medium |

### 攻击清单（计算加权总分，总分≥6且阻塞+高清零方可通过）

```
### L1 攻击审查: <slug>

| # | 检查项 | 结果 | 攻击证据 |
|---|--------|:----:|---------|
| 1 | spec 自洽性 | ... | ... |
| ... | ... | ... | ... |

## 攻击清单（按严重度排序）

Q1 (严重度: 阻塞/高/中/低, 分值: 3/2/1/0) — [位置] 问题描述 → 建议修正
Q2 ...

总分: N (阻塞+高: K 项 → 已清零/未清零)
结论: PASS (总分≥6, 阻塞+高已清零) 或 FAIL
```

### 常见退回场景

- spec 说"用户可看到结果"，flow 里没有 resultNode → Q: 退回补 resultNode
- 验收路径写了入口但没写中间步骤 → Q: 退回补充点击路径
- wire 全是 bar/panel/table/drawer 通用组件 → Q: 退回按业务布局重做
- wire 元素缺少 `data-node` 属性 → Q: 退回补全 flow 节点映射
- flow 有交互节点但 wire 无对应元素 → Q: 退回补充 wire UI 元素
- wire 有 `data-node` 但 flow 中找不到该节点 → Q: 退回修正映射
- research.md 有方案选型但没写选型依据 → Q: 退回补充决策理由
- 任一规则 ID 在 spec 中存在但 flow 中无对应 → Q: 退回补充 flow 节点
