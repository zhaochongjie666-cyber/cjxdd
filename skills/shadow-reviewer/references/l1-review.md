# L1 Review — 业务设计审查清单

> 用于审查 `research.md`、`project.flow.mermaid`、`spec.md`、`wire` 产物的质量。
>
> 核心目标不是“文件齐不齐”，而是判断 L1 是否：
> 1. 能直接指导实现
> 2. 人类可读
> 3. 覆盖完整业务

## 1. Research 审查

| # | 检查项 | 标准 | 通过 |
|---|:------|:----|:---:|
| R1 | 章节完整性 | 至少包含：流程层面、实现层面、技术选型、调研结论、风险 | ⬜ |
| R2 | 深度充足 | 总行数 > 50，技术选型至少有 2 个方案对比 | ⬜ |
| R3 | 风险覆盖 | 列出至少 2 个业务或技术风险，并给出缓解方案 | ⬜ |

## 2. Flow.mermaid 审查

| # | 检查项 | 标准 | 通过 |
|---|:------|:----|:---:|
| F1 | 语法可渲染 | 通过 `mmdc` 或 `gate-check.sh` 语法检查 | ⬜ |
| F2 | 入口明确 | 第一个节点标注触发来源（如用户/定时任务/外部事件） | ⬜ |
| F3 | 出口明确 | 最后节点标注交付物，使用 resultNode class | ⬜ |
| F4 | 节点拆分 | 节点数 > 15 时已拆分子流程，主流程不超过 15 节点 | ⬜ |
| F5 | 异常分支 | 包含至少 1 条异常/错误处理路径 | ⬜ |
| F6 | 业务线规范 | 跨业务线连接必须通过接口节点（API Gateway/Event Bus），禁止直接连内部节点 | ⬜ |

## 3. Spec 审查

| # | 检查项 | 标准 | 通过 |
|---|:------|:----|:---:|
| S1 | 规则 ID 格式 | 每条规则标注 `<slug>-R01` 格式 ID，连续无跳号 | ⬜ |
| S2 | 规则覆盖 | project.flow.mermaid 中的每个关键步骤在 spec 中有对应规则 | ⬜ |
| S3 | 无矛盾 | 无两条规则对同一场景给出矛盾指令 | ⬜ |
| S4 | 验收路径可执行 | 验收步骤具体到可直接操作（禁止"检查是否正常"等模糊描述） | ⬜ |
| S5 | 实现指导性 | 工程师能直接看出接口/动作、状态、校验、错误、依赖、副作用 | ⬜ |
| S6 | 人类可读性 | 标题/状态/文案优先使用业务语言，非纯工程黑话 | ⬜ |
| S7 | 业务完整性 | 覆盖主流程、异常、边界、权限、重试、回滚、人工兜底 | ⬜ |
| S8 | 无模糊表达 | 不大量出现“相关/必要时/适当/系统处理/触发通知”等空话 | ⬜ |
| S9 | 数据约束具体 | 字段、格式、唯一性、默认值、枚举、脱敏、保留期足够明确 | ⬜ |
| S10 | 依赖与副作用明确 | 外部依赖、失败降级、通知、审计、日志、事件清楚 | ⬜ |

## 4. Wire 审查（如涉及前端）

| # | 检查项 | 标准 | 通过 |
|---|:------|:----|:---:|
| W1 | UI 映射 | flow 中所有用户交互节点在 wire 中有对应区域 | ⬜ |
| W2 | 业务术语 | 区域使用业务术语标注（如"邮箱输入框"而非"box"） | ⬜ |
| W3 | 非空 | 包含实际交互元素，不仅是占位符 | ⬜ |
| W4 | 状态可见 | 页面元素能体现关键状态、关键操作、关键反馈 | ⬜ |
| W5 | 规则对齐 | 关键页面区域能映射到 spec 规则或状态 | ⬜ |

## 输出格式

```markdown
## L1 Review Report: <slug>

| 检查项 | 状态 | 备注 |
|:------|:---:|:----|
| R1-R3 | ✅/⚠️/❌ | ... |
| F1-F6 | ✅/⚠️/❌ | ... |
| S1-S4 | ✅/⚠️/❌ | ... |
| W1-W3 | ✅/⚠️/❌/N/A | ... |

### 🔍 发现的具体问题（FAIL/WARN）
1. **文件:行/章节** — 问题描述（严重度）
2. ...

### 🛠 建议修改（如需打磨模式）
...
```
