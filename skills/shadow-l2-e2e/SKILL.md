# Shadow·BDD+CM — 穷尽覆盖验收

## 角色

BDD 帮你回答"系统应该表现出什么行为"，而不是"代码应该通过什么测试"。
**覆盖矩阵（Coverage Matrix）** 帮你回答"我怎么知道测全了？"
**UAT 用户验收剧本（User Acceptance Script）** 帮你回答"真实用户会不会用、能不能按真实路径完成工作？"
**用户旅程覆盖（User Journey Coverage）** 帮你回答"真实用户在真实生产环境中到底怎么用系统，测的场景是不是用户真正经历的？"
**四层覆盖完整性（Coverage Completeness）** 帮你回答"每个业务线、每个页面、每个交互点、每个 API 端点是否都被端到端测试覆盖了？"

**穷尽不是指测无限场景，而是指对每条规则都系统性地枚举所有已知的测试维度，
确保每个维度至少有一个场景覆盖。没有覆盖矩阵的 e2e，没法证明测全了。**

### 前端浏览器操作优先原则

**L2 真实场景和 UAT 剧本的第一表达形式是真实的前端浏览器操作**，不是 API 调用序列，不是后端内部函数调用。

用户在真实生产环境中是这样用系统的：
1. 打开浏览器，输入 URL 或点击书签
2. 看到页面，阅读内容，点击按钮、填写表单、选择选项
3. 等待页面反馈（loading 动画、成功提示、错误信息、页面跳转）
4. 在新页面上查看结果、继续操作或退出

因此：
- **前端项目的真实场景**必须用浏览器可见的操作语言描述：打开页面、看到元素、点击按钮、填写输入框、选择下拉选项、等待页面跳转、验证页面内容。禁止用 API 调用替代用户浏览器操作。后端 API 调用只作为数据准备和断言验证的补充手段。
- **纯后端项目的真实场景**用 HTTP API 操作语言描述：发送请求、检查状态码、验证响应体、断言数据库状态。UAT 操作脚本必须能由 API scenario replay（如 `curl` 或 `httpx`）执行。维度 13（UX 反馈）和维度 14（浏览器误操作）标记为 N/A。
- **UAT 操作脚本必须能直接翻译为可执行操作**：前端项目 → Playwright 浏览器操作；纯后端项目 → API scenario replay。

参考工具：`references/playwright-cli.md`。

### BDD vs TDD 边界

| 维度 | BDD（本层，L2 E2E） | TDD（Harness 计划测试断言） |
|------|---------------------|----------------|
| **语言** | 业务语言（Given-When-Then） | 代码语言（assert/expect） |
| **读者** | 业务方、产品经理、测试 | 开发者 |
| **粒度** | 用户行为场景（端到端） | 函数/方法/组件（单元/集成） |
| **产出** | e2e.md + 覆盖矩阵 + uat-script.md | .py/.ts 测试代码文件 |
| **位置** | `.shadow/L2-e2e/` | 项目 `tests/` 目录 |
| **运行时机** | L6 Deploy 验收时手工/半自动化验证 | 每次 commit 后自动运行 CI |
| **关注点** | "系统做了什么"、"测全了什么" | "代码对不对" |
| **举例** | "用户确认订单后，订单状态变为已确认" | `assert order.status == "Confirmed"` |

**关键**：BDD 场景是**验收标准**，不是测试代码。TDD 测试是 BDD 场景的**代码级验证**。
覆盖矩阵是两者的**桥梁**——矩阵中的每个格子至少对应一个 BDD 场景和一个 TDD 测试。

UAT 用户验收剧本是 BDD 的落地形态：它必须像真实用户一样，从登录、导航、操作、等待、查看反馈到退出完整走一遍系统。

### 生产级验收边界

L2 设计用例时必须以“我愿意在真实工作中依赖它”为验收标准。功能都实现不等于验收通过；用例必须证明真实用户可以拿真实数据完成真实工作，系统出错时可发现、可解释、可恢复、可追责。

每条 P0 用户路径必须覆盖以下共性闭环：

| 闭环 | L2 必须写进用例的内容 |
|------|------------------------|
| 业务闭环 | 真实角色从真实入口完成完整工作流，不依赖工程师补步骤 |
| 数据闭环 | 创建/处理/查询/导出/回溯一致，重启后仍可查 |
| 权限闭环 | 登录、角色、授权、越权拒绝、审计日志 |
| 状态闭环 | 排队/处理中/成功/失败/取消/返工等状态可解释、可恢复 |
| 异常闭环 | 网络失败、任务失败、部分失败、重复提交、并发冲突 |
| UX 闭环 | 下一步、成功结果、失败原因、重试/修正入口清楚 |
| 集成闭环 | 前端/API → 后端 → DB/对象存储/队列/外部服务 |
| 运维闭环 | 日志、trace、告警、重试、回滚、数据修复入口 |
| 性能闭环 | 目标数据量、并发量、任务量的最低验收线 |
| 证据闭环 | L6 需要采集的截图、network、日志、DB/存储证据 |

引用标准：`references/production-acceptance-contract.md`。

### 真正可用边界

L2 写的是验收标准，因此必须明确什么证据能证明“真正可用”：
- 真实账号或 seed 用户登录，不允许假登录或硬编码用户。
- 真实页面/API 执行业务动作，不允许直接调用内部函数替代用户路径。
- 业务数据必须进入真实持久化层，并在后续步骤查询或复用。
- 核心 UAT 必须包含最终业务状态断言，例如列表可见、详情可查、DB/存储状态一致。
- HTTP 200/201 只是连通性证据，不能单独作为业务成功断言。

引用标准：`references/real-usability-contract.md`。

## 覆盖矩阵（Coverage Matrix）—— 穷尽的核心工具

**覆盖矩阵**是 L2 的核心产出物，它与 e2e.md 并列。矩阵枚举每条规则的每个测试维度，
确保无遗漏。每行是一个测试点，每列是覆盖状态。

### 覆盖维度（如果 `.shadow/scale.md` 存在，按 `coverage_dimensions` 参数取维度数；否则默认 14 维）

对 **每条规则**，覆盖矩阵必须系统性地枚举以下维度。
维度 1-10 是**规则维度**（从 spec 规则出发），维度 11-14 是**用户维度**（从真实用户浏览器操作出发）。

**S 级项目（8 维）**：仅维度 1-8。
**M 级项目（10 维）**：维度 1-10。
**L 级项目（14 维）**：全部维度。

| # | 维度 | 说明 | 列数示例 |
|---|------|------|---------|
| 1 | **主流程（Happy Path）** | 规则正常执行的所有路径变体 | 至少 1 |
| 2 | **异常路径（Error Path）** | 每条规则中每个可识别的错误条件（来自 spec.md 异常描述） | = 异常数 |
| 3 | **前置条件违反（Precondition Violation）** | 每条前置条件不满足时的行为 | = 前置条件数 |
| 4 | **权限检查（Permission/Role）** | 每个角色对该规则的行为（谁可以/谁不可以） | = 角色数 |
| 5 | **状态机转换（State Machine）** | 每条规则触发的合法状态转换 + 禁止的非法转换 | 合法+非法 |
| 6 | **边界（Boundary）** | 参数/数据的空值、最小值、最大值、超长、特殊字符 | 至少 2 |
| 7 | **副作用/领域事件（Side Effects）** | 每个领域事件的发布断言（必须发布/必须不发布/载荷校验） | = 事件数×2 |
| 8 | **数据完整性（Data Integrity）** | 操作后的数据状态变化（创建/更新/删除的数据正确性） | 至少 1 |
| 9 | **幂等性（Idempotency）** | 重复执行同一操作时的行为（如适用） | 0 或 1 |
| 10 | **并发/竞态（Concurrency）** | 并发操作时的行为（如适用） | 0 或 1 |
| 11 | **会话连续性（Session Continuity）** | 浏览器跨会话恢复、关闭标签页后重新打开、断点续作、多标签页切换、会话过期后重新登录 | 至少 1 |
| 12 | **用户误操作（User Error）** | 浏览器中误点、后退按钮、刷新页面、双击提交按钮、撤销操作、误删后恢复 | 至少 1 |
| 13 | **环境多样性（Environment）** | 不同浏览器/网络条件/屏幕尺寸/设备类型对用户操作的影响 | 0 或 1 |
| 14 | **UX 反馈点（UX Feedback）** | 每个浏览器操作的 loading/empty/error/success/notification 反馈验证 | 至少 1 |

维度 11-14 判定规则：
- 维度 11-12：对用户直接操作的规则**强制覆盖**（纯后台规则可 N/A，需说明理由）。
- 维度 13：有前端项目时**强制覆盖**（纯后端项目可 N/A）。
- 维度 14：对每个用户可感知的浏览器操作**强制覆盖**。
- 所有 N/A 必须在矩阵中写明理由，不能省略行。

### P0/P1 优先级标注

每个覆盖矩阵行和每个 UAT 剧本必须标注 P0 或 P1。L6 依赖此标注决定验收范围。

**P0 判定规则**（满足任一即为 P0）：
- 核心业务路径（用户完成主要目标的最短路径上的每一步）
- 涉及金钱/数据安全/权限校验的场景
- spec.md 中标注为 P0 的规则对应的场景
- 失败后用户无法自行恢复的场景

**P1 判定规则**：
- 非核心路径的分支/边界/异常场景
- 用户体验优化类场景（如 loading 状态、toast 提示）
- 高频但不影响业务闭环的场景

优先级标注在覆盖矩阵的"优先级"列，在 UAT 剧本标题中以 `[P0]` 或 `[P1]` 前缀标注。

### 每条规则必须输出一个覆盖矩阵

覆盖矩阵与场景描述（Given-When-Then）一一对应。矩阵在前，场景在后。

## 怎么做

### 0. 用户画像分析（前置步骤）—— 读 L1 + 独立发散 + 对比校验

**三步流程**：先读 L1 已有的用户画像 → 再独立发散 → 对比发现 L1 遗漏。

#### 0-1. 读 L1 用户画像

读 `intent.md` 和 `research.md` 中 L1 Research 已产出的用户画像发散清单和画像详情。

**额外输入**：检查 `research.md` 末尾是否有"收敛丢弃清单"。如果存在，读入清单中的被丢弃场景，在独立发散时判断是否需要从测试验收视角恢复其中的画像——不是恢复所有被丢弃的，而是问"从测试视角看，这个被丢弃的场景是否影响系统的验收完整性？"

#### 0-2. 独立发散（不限于 L1 已有的）

读 spec.md + research.md 统一语言和角色定义，**独立发散式**枚举所有可能的用户画像。

**核心原则：不要只列业务方告诉你的角色。不要只看 L1 已有的。要主动从测试验收视角发散——谁会用这个系统？谁会误用？谁会滥用？谁会在意外场景下使用？L1 是从业务调研视角发散的，L2 是从测试验收视角发散的，两个视角互补。**

用以下 6 个维度穷举用户画像，每个维度至少产出 1 个画像变体：

| 发散维度 | 问题 | 产出 |
|---------|------|------|
| **官方角色** | spec.md / research.md 中定义了哪些角色？每个角色 1 个画像。 | 基准画像 |
| **技能梯度** | 每个官方角色中，新手/熟练/专家分别怎么操作？操作习惯差异？ | 每角色 1-3 个画像变体 |
| **使用频率** | 高频用户（每天）/ 中频用户（每周）/ 低频用户（偶尔）/ 首次用户，操作路径有何不同？ | 每角色 1-4 个画像变体 |
| **极端用户** | 谁会大规模批量操作？谁会频繁撤销重做？谁会同时开多个标签页？谁会用键盘快捷键？ | 至少 2 个极端画像 |
| **误用/滥用者** | 谁会尝试越权操作？谁会疯狂点击？谁会输入垃圾数据？谁会尝试 XSS/注入？ | 至少 1 个安全画像 |
| **意外场景用户** | 谁会在手机上误触？谁会在慢网络下操作？谁会在公共电脑上忘记退出？ | 至少 1 个意外画像 |

**画像数量要求**：
- 最少 5 个画像（官方角色 + 技能梯度 + 极端 + 误用 + 意外）
- 每个画像必须有明确区分度——如果两个画像的操作路径完全相同，合并

```markdown
## 用户画像

### 画像 P-01：<角色名>-<变体标签>

| 字段 | 内容 |
|------|------|
| 角色基类 | 来自 research.md 的哪个官方角色 |
| 变体标签 | 新手/熟练/专家/极端/误用/意外 |
| 核心目标 | 该画像登录系统最想完成的 1-3 件事 |
| 典型工作日 | 该画像每天在系统中的高频操作和高峰时段 |
| 浏览器操作路径 | 从打开浏览器到完成核心目标的完整点击/导航/操作路径 |
| 操作特征 | 该画像独有的操作习惯（如：喜欢批量操作/经常用浏览器后退/习惯 Ctrl+S） |
| 技能水平 | 专家/熟练/新手 → 决定引导提示和防呆设计的需求 |
| 使用频率 | 高频(每天)/中频(每周)/低频(每月)/首次 → 决定会话恢复和操作记忆需求 |
| 常见痛点 | 该画像最容易遇到的操作困难和困惑 |
| 生产数据特征 | 该画像日常处理的数据量级、数据状态多样性 |
| 预期操作路径数 | 该画像可能走的操作路径数量估算（用于后续穷举） |

### 画像发散清单

| 画像ID | 角色基类 | 变体标签 | 核心区分度 | 预期路径数 |
|--------|---------|---------|-----------|-----------|
| P-01 | {角色1} | 熟练用户 | 熟练路径，不看引导，直接操作 | ~8 |
| P-02 | {角色1} | 新手用户 | 需要引导，容易点错，依赖提示 | ~12 |
| P-03 | {角色1} | 极端批量 | 大规模批量操作，性能敏感 | ~5 |
| P-04 | {角色2} | 官方角色 | 基准操作路径 | ~6 |
| P-05 | 任意 | 误用者 | 尝试越权/输入非法数据/疯狂点击 | ~10 |
| P-06 | 任意 | 意外场景 | 手机误触/慢网络/公共电脑 | ~6 |
| ... | ... | ... | ... | ... |
```

画像产出嵌入 e2e.md 的"用户画像"章节。

#### 0-3. 与 L1 对比校验

将 L2 独立发散的用户画像与 L1 Research 已有的画像对比：

| 对比维度 | 检查方法 | 发现遗漏时 |
|---------|---------|-----------|
| L2 有但 L1 没有的画像 | L2 发散清单 - L1 发散清单 | 进入 L1 回溯清单（§0.3） |
| L2 有但 L1 没有的变体标签 | 按角色基类对比变体标签 | 进入 L1 回溯清单 |
| L1 有但 L2 没考虑到的画像 | 反向检查 L1 画像是否被 L2 覆盖 | L2 补充该画像 |
| 区分度不足 | L1 和 L2 各自的画像是否有明确区分 | 合并或拆分 |

### 0.1 用户旅程穷举（强制步骤）—— 读 L1 + 独立发散 + 对比校验 + 交叉矩阵

**三步流程**：先读 L1 已有的旅程穷举 → 再独立发散 → 对比发现 L1 遗漏 → 构建交叉矩阵。

#### 0.1-1. 读 L1 旅程穷举

读 `research.md` 中 L1 Research 已产出的旅程图和按画像汇总覆盖率表。理解 L1 已经识别了哪些用户操作路径（用业务场景语言描述）。

**额外输入**：检查 `research.md` 末尾是否有"收敛丢弃清单"。如果存在，读入被丢弃的旅程，在独立发散时判断其中哪些应恢复。

#### 0.1-2. 独立发散（不限于 L1 已有的）

**基于 L2 自己的用户画像发散，为每个画像独立穷举所有可能的操作路径。不是画一条主线就完事——要发散出每条分支、每个拐点、每个可能的操作序列。L1 是从业务视角穷举的，L2 从测试验收视角穷举，两个视角互补。**

对每个画像，按以下 5 个层次穷举操作路径：

| 层次 | 穷举目标 | 方法 |
|------|---------|------|
| **主线旅程** | 该画像完成核心目标的最佳路径 | 1 条主线 |
| **分支旅程** | 主线上的每个决策点的每个分支 | 每个决策点 × 分支数 |
| **迂回旅程** | 不走最优路径，绕路/回退/重试/走弯路 | 至少 2 条迂回路径 |
| **意外旅程** | 断网/崩溃/超时/会话过期/误操作后的恢复路径 | 至少 1 条意外路径 |
| **探索旅程** | 无目的浏览/第一次使用/尝试所有按钮/输入非法数据/越权尝试 | 至少 1 条探索路径 |

对每个画像，必须逐项检查以下操作路径是否存在，存在则产出旅程：

```markdown
### 迂回旅程
- [ ] 操作到一半点浏览器后退按钮，然后重新前进
```


### 6. 真实场景（Real Scenario）—— 验证可生产性的必经之路

覆盖矩阵保证每条规则的每个维度都被覆盖。但**真实场景**保证这些规则组合起来能支撑一个完整的用户旅程。

覆盖矩阵测的是"每个零件都检查过了"，真实场景测的是"整机能跑"。

#### 真实场景定义

一个真实场景必须：
- **从旅程穷举结果中选取和组合**（不是凭空编造的操作序列，必须对应用户画像发散产出的某条或多条旅程）
- **标注来源旅程编号**（如"基于 P-01 的 J-03 + P-04 的 J-12 组合"）
- **用真实前端浏览器操作语言描述**（打开页面、点击按钮、填写表单、选择选项、等待页面反馈——不是 API 调用，不是内部函数）
- **串联 ≥3 个流程节点**（覆盖一个完整的用户操作链）
- **涉及 ≥2 条规则**（规则间的交互）
- **使用生产级数据**（真实数据结构、真实量级、真实状态多样性——不是 1 条测试数据而是该角色日常处理的量级）
- **包含多个角色**（至少主角+配角，如标注员+审核员）
- **模拟真实浏览器时间线**（打开浏览器→输入URL→看到页面→点击元素→等待反馈→看到结果→继续操作或退出）
- **包含浏览器导航步骤**（从哪进来、点了哪个菜单/链接/按钮到达目标页面）
- **包含浏览器 UX 反馈验证**（每一步用户在浏览器中看到什么：loading 动画/成功提示 toast/错误信息/页面跳转/空状态插图）
- **包含持久化断言**（浏览器操作后，通过页面列表/详情/API/DB 确认数据持久化）
- **包含跨服务断言**（浏览器操作触发后端 API 请求，API 处理后影响真实存储——通过浏览器 network 面板和后端日志双重验证）
- **包含生产依赖断言**（对象存储/队列/异步 worker/外部服务如适用）
- **包含可恢复失败断言**（浏览器中看到错误提示→用户可理解原因→有明确的修正/重试操作入口）
- **包含可追责断言**（审计日志、操作人、时间、对象 ID、trace/request id）
- **包含可依赖性判定**（真实用户在浏览器中是否能独立完成工作，不需要工程师手工补救）
- **包含至少 1 个浏览器用户误操作 + 恢复**（如误点浏览器后退按钮、双击提交按钮、刷新页面、误删后撤销）
- **包含至少 1 个浏览器会话中断 + 恢复**（如关闭浏览器标签页后重新打开、会话过期后重新登录续作）

#### 真实场景数量：不设上限，穷尽到每一处细节

**真实场景的数量没有上限，越多越好。** 下限是"至少 3 个"，但目标不是凑够 3 个就停——目标是把每条规则的每个维度、每个画像的每条旅程、每个页面的每个交互点都通过真实场景覆盖到。

停止条件：当且仅当以下 4 个条件**全部满足**时，真实场景才算穷尽完成：
1. 覆盖矩阵的每一行都至少被 1 个真实场景覆盖
2. 旅程穷举的每条旅程都至少被 1 个真实场景包含
3. 四层覆盖完整性（业务线/页面/交互点/API端点）全部 100%
4. 不存在任何"未被真实场景覆盖"的规则、节点、页面或交互点

以下示例全部使用浏览器操作语言描述，每一步都能直接翻译为 Playwright 交互。

```markdown
**涉及规则**: R11, R12, R13, R15, R18
```

## UAT 用户验收剧本（最终验收源）

每个业务线必须在 `.shadow/L2-e2e/BXX-{slug}/uat-script.md` 中产出用户验收剧本。这个文件是 L6 最终验收的执行源。

UAT 剧本不是"测试说明"，而是可执行的真实用户路径。它必须使用业务角色、真实页面、真实按钮、真实数据和真实等待时间来描述。

### UAT 剧本结构

```markdown
# <slug> 用户验收剧本

## UAT-01：<真实用户目标>

**用户目标**: <用户实际想完成的工作，不写技术目标>
**角色**: <真实角色，如管理员/标注员/审核员>
**浏览器入口**: <完整 URL，如 http://localhost:3000/login>
**涉及流程节点**: BXX-NYY -> BXX-NYY -> BXX-NYY
**涉及规则**: R01, R02, R03
**覆盖页面**: <wire.svg data-page 列表>
**验收数据**:
- 用户账号: <角色账号>（用于浏览器登录）
- 业务数据: <真实字段、真实规模、真实状态>
- 外部依赖: <短信/邮件/OAuth/支付/通知，如适用>
- 浏览器持久化断言: <操作后在浏览器页面中能看到什么——列表/详情/状态标签>
- 数据库持久化断言: <DB/API 层面的最终数据状态>
- 重启后断言: <如为 P0 核心数据，重启服务后在浏览器中重新查询仍可见>

### 浏览器操作脚本（每一步对应 Playwright 操作）
1. 打开浏览器，访问 `<URL>`。→ `playwright open <URL>`
2. 在用户名输入框输入 `<account>`，密码框输入 `<password>`，点击"登录"按钮。→ `fill` + `click`
3. 等待页面跳转到首页，确认首页加载完成（看到导航栏）。→ `waitForURL` + `waitForSelector`
4. 在导航栏中点击"<菜单名>"，等待目标页面加载。→ `click` + `waitForLoadState`
5. 在目标页面中，<点击/填写/选择/拖拽/上传具体元素>。→ `click`/`fill`/`select`/`drag`/`upload`
6. 等待操作反馈（loading 消失，成功/错误提示出现）。→ `waitForSelector`
7. 在浏览器中确认操作结果（页面文字/列表更新/状态标签变化）。→ `assertText`/`assertVisible`
8. [如为 P0] 打开新标签页，访问 <查询页面URL>，确认数据可查。→ `open` + `assert`
9. [如为 P0] 重启服务后，在浏览器中刷新页面，确认数据仍在。→ `reload` + `assert`
10. 点击右上角头像，选择"退出登录"。→ `click`

### 通过标准
- 浏览器页面反馈: <每一步用户在浏览器中看到什么——具体元素、文字、状态>
- 浏览器数据可见: <操作后在浏览器页面中列表/详情可见的最终状态>
- 数据库一致: <DB/API 查询结果与浏览器页面显示一致>
- 副作用验证: <浏览器通知/邮件截图/文件下载等>
- 错误处理: <失败时浏览器中显示什么错误信息，用户如何修正>
- 浏览器网络请求: <关键 API 请求 URL、方法、状态码（通过 DevTools Network 或 Playwright requests 验证）>

### 证据要求
- 浏览器截图: 每个关键步骤的截图（起始页、操作中、操作后反馈、最终结果页）
- 浏览器网络: 关键 API 请求 URL、方法、状态码
- 数据证据: API 响应/DB 查询/导出文件校验
- 日志证据: 如涉及异步任务或外部服务，记录任务/回调/通知日志
```

### UAT 通过门槛

- 每个核心角色必须有 UAT 剧本覆盖其所有核心目标（不是 1 条就够，而是覆盖该角色的每一条旅程）。
- 每条核心业务主链路必须有 UAT 剧本覆盖其所有分支路径。
- UAT 剧本数量不设上限，目标是将每条旅程穷举结果都落实到可执行的 UAT 操作脚本中。
- 每条 UAT 剧本必须串联 >=3 个 BXX-NYY 节点。
- 每条 UAT 剧本必须覆盖 >=2 条 RXX 规则。
- 每个涉及外部服务的 UAT 必须包含成功路径和失败/超时/重试路径。
- **每条 UAT 剧本的操作步骤必须用真实浏览器操作语言描述**（打开页面/点击按钮/填写表单/选择选项/等待反馈），能直接翻译为 Playwright 交互序列。
- **前端项目的 UAT 必须能由 Playwright 按真实浏览器操作执行**（不是 curl API 调用）。
- **纯后端项目的 UAT 必须能由 API scenario replay 按真实 HTTP 请求执行**。
- **每条 UAT 必须包含浏览器可见的反馈验证**（loading/success/error/notification 的具体文字或元素状态）。
- **每条 UAT 必须包含导航路径**（从登录到目标页面的完整点击路径，不能省略中间步骤）。
- 每条 P0 UAT 必须包含最终数据状态证据；有持久化服务时必须包含重启后在浏览器中仍可查询的断言。
- 每条 P0 UAT 必须包含至少 1 个浏览器用户误操作验证（双击提交/后退按钮/刷新页面）。

### 真实场景 vs 覆盖矩阵

| 维度 | 覆盖矩阵 | 真实场景 |
|------|---------|---------|
| 目标 | 每条规则的每个维度都覆盖 | 验证真实用户旅程 |
| 粒度 | 单规则、单维度 | 多规则、多节点串联 |
| 数据 | 典型值 | 生产级数据 |
| 角色 | 单角色 | 多角色协同 |
| 异常 | 前置条件违反 | 真实环境故障（断网/超时/并发） |
| 可替代性 | 不可替代 | 不可替代 |

**两者缺一不可**。只有覆盖矩阵没有真实场景 → 你无法证明系统在实际使用中不会出问题。
只有真实场景没有覆盖矩阵 → 你不知道哪个维度的测试漏了。

### 7. BDD 最佳实践

- **一个场景一个行为** — 多个行为混在一起时，失败不知道原因
- **声明式 > 命令式** — 描述"做了什么"，不是"点了哪个按钮"
- **3-7 步** — 超过说明场景太大
- **术语用统一语言** — 业务方能看懂
- **@covers** — 每个场景标注覆盖了哪条规则

### 7. 断言具体化

每个 Then 必须：
- 状态怎么变（如 status == "Confirmed"）
- 事件发没发（如 OrderPlaced 已发布）
- 数据怎么变（如库存 -1）
- **错误码明确**（如 400 INVALID_LABEL，不是笼统的"报错"）

禁止"功能正常"。

### 8. Spec 漏洞检测与回溯（SDD→BDD 双向校验）

构建覆盖矩阵时如果发现：

- **规则未定义** — 某测试点在 spec.md 中找不到对应规则
- **规则歧义** — 某测试点需要的数据/状态/权限在 spec.md 中描述模糊
- **规则冲突** — 多条规则对同一测试点给出矛盾要求
- **遗漏异常** — 某异常路径 spec 未定义
- **遗漏维度** — 某规则关键的测试维度在 spec 中缺信息

→ **立即回溯**：将发现追加到 spec.md 的"待修正"清单

### 综合覆盖率计算

```
综合覆盖率 = (
    业务线覆盖率 × 0.25 +
    页面覆盖率   × 0.25 +
    交互点覆盖率 × 0.25 +
    API 端点覆盖率 × 0.25
)
目标 = 100%（穷尽覆盖，不设上限）
```

综合覆盖率与规则×维度矩阵覆盖率独立计算。两者都必须达标：
- 规则×维度矩阵覆盖率 = 100%（穷尽覆盖，每一行都必须有场景）
- 四层覆盖完整性综合覆盖率 = 100%（穷尽覆盖，每一项都必须被场景包含）

## 约束

- 术语必须来自 research.md 统一语言
- 每个场景绑定 ≥1 条 @covers
- 领域事件必须有发布/不发布断言
- **BDD 场景用业务语言，不写代码**（代码测试是 Harness 计划测试断言的职责）
- **场景粒度是用户行为，不是函数调用**（函数测试是 Harness 计划测试断言的职责）
- **e2e.md 是验收文档，不是测试代码**（验收文档可以被 L6 Deploy 用来验证，但不能替代代码测试）
- **每个 e2e.md 末尾必须包含 Spec 回溯清单**（无发现时写"无发现"）
- **回溯发现的问题必须在 spec.md 中有对应修正记录**
- **每条规则必须有覆盖矩阵**，矩阵行数 = 实际枚举的测试点数
- **覆盖矩阵的每个维度至少 1 行**（第 9-10 维可 N/A，需说明理由）
- **覆盖度 < 100% 时，e2e 不能算完成**——必须继续补充场景直到每一项都被覆盖
- **L5 Harness 测试的 @covers 必须能映射到覆盖矩阵行**（每条 @covers 对应一个矩阵测试点）
- **每个业务线至少 3 个真实场景起步，不设上限，穷尽到覆盖矩阵每一行和旅程穷举每一条都被场景包含为止**，串联 ≥3 个流程节点、≥2 条规则、≥2 个角色
- **真实场景必须使用生产级数据**（真实数据结构、合理数据量、真实业务术语）
- **真实场景必须包含至少 1 个真实环境异常**（断网/超时/并发/数据冲突）
- **P0 UAT 必须验证真实持久化和跨服务链路**，不能只断言 HTTP 200/201
- **禁止把 mock DB、InMemoryRepository、假登录路径写成最终验收通过路径**
- **覆盖矩阵必须包含维度 11-14**（用户维度），对用户直接操作的规则强制覆盖，N/A 必须写理由
- **每个核心角色必须有发散式用户画像**（至少 5 个画像：官方角色 + 技能梯度 + 极端 + 误用 + 意外）
- **L2 必须独立发散用户画像和旅程**，不限于 L1 已有的，从测试验收视角补充
- **L2 发散后必须与 L1 对比校验**，发现遗漏时进入回溯协议
- **回溯由 Agent Worker 派 L1 Research 执行**，L2 不自行修改 research.md / intent.md
- **旅程编号区分来源**：J-L1-XX 为 L1 旅程，J-T-XX 为 L2 测试视角新增
- **每个画像必须有用户旅程穷举**，产出主线/分支/迂回/意外/探索 5 类旅程
- **旅程穷举必须产出交叉矩阵**：规则×旅程、页面×旅程、交互点×旅程
- **穷举完成标准**：总旅程数 ≥ 画像数 × 5，每条规则被 ≥2 个画像覆盖，每个页面被 ≥2 个画像覆盖
- **真实场景必须基于旅程穷举结果设计**，从旅程池中挑选和组合
- **真实场景必须用浏览器操作语言描述**（打开页面/点击/填写/选择/等待反馈），禁止用 API 调用或内部函数描述操作步骤
- **UAT 操作脚本的每一步必须标注对应 Playwright 操作**（click/fill/select/waitForSelector/screenshot），确保可直接翻译为浏览器自动化
- **真实场景必须包含至少 1 个浏览器用户误操作+恢复和 1 个浏览器会话中断+恢复**
- **综合覆盖度（规则×维度 × 四层覆盖完整性）目标 100%，穷尽到每一项都被场景包含**，不允许出现"未被任何场景覆盖"的规则、节点、页面或交互点
- **生产数据必须反映真实量级和状态多样性**（不是 1 条测试数据，而是用户日常处理的数据规模和不同状态）
- **覆盖矩阵维度 11-14（用户维度）的测试点也必须用浏览器操作语言描述**
- **e2e.md 必须包含四层覆盖完整性章节**：业务线覆盖表、页面覆盖表、交互点覆盖表、API 端点覆盖表
- **e2e.md 必须包含 L1 回溯清单**（与 Spec 回溯清单并列），无遗漏时写"无遗漏"
- **四层覆盖完整性中的缺口必须在覆盖简报中标注**，不能省略
