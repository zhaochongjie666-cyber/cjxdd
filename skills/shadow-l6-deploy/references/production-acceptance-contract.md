# Production Acceptance Contract — 生产级验收契约

验收通过的标志不是“功能都实现了”，而是：

> 真实用户愿意在真实工作中依赖它；真实数据、真实责任、真实失败都能交给系统处理。

适用于生产级前后端项目，包括回灌平台、仿真平台、数据标注平台、任务平台、运营后台等。该契约是 L2 用例、L5 Harness 测试、L6 UAT、UX Review、Checker 的共同验收口径。

## 共同验收维度

| 维度 | 必须证明 |
|------|----------|
| 业务闭环 | 用户能从真实入口完成 P0 工作流，不依赖工程师手工补步骤 |
| 数据闭环 | 数据创建、处理、查询、导出、回溯一致，重启后不丢 |
| 权限闭环 | 登录、角色、授权、越权拒绝、审计日志真实生效 |
| 状态闭环 | 任务状态、失败状态、处理中状态、完成状态可解释、可恢复 |
| 异常闭环 | 网络失败、任务失败、部分失败、重复提交、并发冲突都有处理 |
| UX 闭环 | 用户知道下一步做什么，失败后知道怎么修，成功后知道结果在哪 |
| 集成闭环 | 前端 → 后端 → DB/对象存储/队列/外部服务真实打通 |
| 运维闭环 | 日志、指标、告警、重试、回滚、备份、数据修复路径存在 |
| 性能闭环 | 在目标数据量、并发量、任务量下仍可用 |
| 证据闭环 | 每个 PASS 都有截图、日志、trace、DB 查询、报告或测试结果支撑 |

## 平台类 P0 共性场景

### 回灌 / 数据导入平台

- 用户上传或选择一批真实数据。
- 系统校验格式、权限、去重、幂等。
- 后端异步处理，前端可见进度。
- 部分失败时展示失败原因、失败行、可重试范围。
- 重复提交不会污染数据。
- 处理结果可查询、可导出、可对账。
- 服务重启后任务状态和结果仍存在。

### 仿真平台

- 用户创建仿真配置，参数校验真实执行。
- 提交任务后进入队列，前端可见排队/运行/成功/失败/取消状态。
- 结果可查询、对比、下载。
- 同一输入在可控条件下可复现。
- 失败任务有日志、错误原因、重跑入口。
- 大任务有资源限制、超时处理和失败恢复路径。

### 数据标注平台

- 管理员创建项目、导入数据、分配任务。
- 标注员领取任务、提交标注。
- 审核员审核、驳回、返工、通过。
- 并发标注、重复领取、权限越界被正确处理。
- 标注结果能导出，并与原始数据一一对应。
- 质量抽检、冲突处理、历史版本、操作审计可追踪。
- 刷新页面、重新登录、服务重启后工作状态不丢。

## PASS 标准

生产级验收必须同时满足：

- P0 用户路径 100% 在真实运行系统中跑通。
- 真实数据写入真实持久化层，并可通过后续页面/API 查询。
- 服务重启后关键业务数据和任务状态仍存在。
- 真实登录、鉴权、越权拒绝、审计日志生效。
- 失败、重试、部分失败、并发冲突、重复提交路径可用。
- 有前端时，必须有真实浏览器路径、截图、network trace 和用户可见反馈。
- 后端必须有日志、trace、DB/存储证据和最终数据状态。
- 性能达到目标数据量、并发量、任务量的最低验收线。
- 部署、诊断、回滚、数据修复路径清楚。

## 直接 FAIL 信号

- 只证明功能代码存在，没有真实用户路径。
- 只看 API 200/201、服务启动或单元测试总数。
- 使用 InMemoryRepository、mock DB、假登录冒充验收通过。
- P0 UAT 没有截图、网络、日志、DB/存储证据。
- 失败路径只写“联系管理员”，没有可定位原因、重试或恢复路径。
- 用户完成操作后不知道结果在哪、下一步做什么、失败怎么处理。
- 数据无法对账、无法导出、无法追溯、重启后丢失。
- 没有越权拒绝、审计日志或真实权限边界验证。

## 一句话标准

真实用户可以拿真实数据完成真实工作；系统出错时可发现、可解释、可恢复、可追责。
