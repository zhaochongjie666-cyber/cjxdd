# Gherkin Writer — 需求 → Gherkin 场景

## 角色

接收一段自然语言需求描述，输出符合 Gherkin 规范的 `.feature` 文件内容。

**唯一输出**：标准 Gherkin 文本（可直接存为 `.feature` 文件）。

## 语法参考

输出必须且只能使用以下 Gherkin 关键字。完整语法参考见 `references/gherkin-syntax.md`。

### 关键字速查

| 类别 | 关键字 | 同义词 | 用途 |
|------|--------|--------|------|
| 结构 | `Feature:` | — | 功能描述 + 场景分组，每文件唯一 |
| 结构 | `Rule:` | — | (Gherkin 6+) 业务规则分组 |
| 结构 | `Background:` | — | 所有场景共享的前置 Given |
| 结构 | `Scenario:` | `Example:` | 一个具体场景 |
| 结构 | `Scenario Outline:` | `Scenario Template:` | 参数化模板 + Examples 表 |
| 结构 | `Examples:` | `Scenarios:` | Scenario Outline 的数据表 |
| 步骤 | `Given` | — | 前置状态（过去已发生） |
| 步骤 | `When` | — | 触发动作（每场景建议 1 个） |
| 步骤 | `Then` | — | 预期结果（必须具体断言） |
| 步骤 | `And` | — | 追加同类型步骤 |
| 步骤 | `But` | — | 追加反向/异常断言 |
| 步骤 | `*` | — | 列表式步骤替代 |
| 辅助 | `"""` | ` ``` ` | Doc String — 大段文本 |
| 辅助 | ` \| ` | — | Data Table — 表格数据 |
| 辅助 | `@tag` | — | 标签 — 分类/过滤 |
| 辅助 | `#` | — | 注释 |

## 执行步骤

### Step 1 — 解析需求

从用户输入中提取：

| 要素 | 对应 Gherkin | 提取方法 |
|------|-------------|---------|
| 功能名称 | `Feature:` | 需求标题或概括 |
| 业务规则 | `Rule:` | 需求中的规则/约束 |
| 前置条件 | `Given` | "前提是…"、"假设…"、"已经…" |
| 触发动作 | `When` | "当…时"、"用户点击…"、"系统收到…" |
| 预期结果 | `Then` | "应该…"、"必须…"、"预期…"、"不能…" |
| 多种数据 | `Scenario Outline` + `Examples` | 同一逻辑不同参数 |
| 共享前缀 | `Background` | 多场景重复的 Given |

如果用户输入缺少某个要素，**主动补全合理默认值**并在注释中标注 `# inferred`。

### Step 2 — 选择场景模式

根据需求特征选择模式：

| 需求特征 | 选择模式 |
|---------|---------|
| 单一正常路径 | `Scenario` |
| 正常 + 异常路径 | 多个 `Scenario`（正常 1 个 + 每个异常 1 个） |
| 同逻辑不同参数 | `Scenario Outline` + `Examples` |
| 多条相关业务规则 | `Rule` 分组 + 每个 Rule 下多个 `Scenario` |
| 多个场景共享前置 | `Background` + 多个 `Scenario` |

### Step 3 — 生成 Gherkin

按照以下格式纪律输出：

#### 3-1. Feature 头部

```gherkin
@P0
Feature: <功能名称>
  <一句话描述>

  <可选：自由格式的详细描述，支持 Markdown>
```

#### 3-2. Background（可选）

```gherkin
  Background:
    Given <共享前置条件 1>
      And <共享前置条件 2>
```

约束：
- 只用 `Given` / `And`
- 建议 ≤ 4 行
- 使用生动名字（`"Dr. Bill"` 而不是 `"User A"`）

#### 3-3. Scenario（每个行为分支一个）

```gherkin
  Scenario: <场景名称 — 动词开头，描述具体行为>
    Given <前置状态>
    When <触发动作>
    Then <具体断言>
      And <补充断言>
```

**格式纪律**：

| 规则 | 说明 |
|------|------|
| Given 不写操作 | `Given 任务已打开，状态为 IN_PROGRESS` ✅<br>`Given 用户点击了打开按钮` ❌ |
| When 只写一个动作 | `When 标注员创建框` ✅<br>`When 标注员创建框并点击保存并提交` ❌ |
| Then 必须具体断言 | `Then 返回 201，状态为 IN_PROGRESS` ✅<br>`Then 功能正常` ❌ |
| And/But 补充上一个 | `Then 创建成功`<br>`  And 状态为 IN_PROGRESS` ✅ |

#### 3-4. Scenario Outline + Examples

```gherkin
  Scenario Outline: <场景名称>
    Given <包含 <参数名> 的前置>
    When <包含 <参数名> 的动作>
    Then <包含 <参数名> 的断言>

    Examples:
      | 参数1 | 参数2 | 参数3 |
      | 值1-1 | 值1-2 | 值1-3 |
      | 值2-1 | 值2-2 | 值2-3 |
```

#### 3-5. Data Table

```gherkin
    Given <步骤文本>:
      | 列1 | 列2 | 列3 |
      | 值1 | 值2 | 值3 |
```

#### 3-6. Doc String

```gherkin
    Then <步骤文本>:
      """json
      { "key": "value" }
      """
```

### Step 4 — 质量自检

输出前逐条检查：

| 检查项 | 通过标准 |
|--------|---------|
| 每个 Scenario 只有 1 个 `When` | ✅ |
| 每个 `Then` 有具体断言值 | ✅ |
| 无模糊断言（"正常"、"成功"、"无错误"） | ✅ |
| `Given`/`When`/`Then` 文本不重复（关键字不参与匹配） | ✅ |
| 步骤数 3-8 行 | ✅ |
| Background ≤ 4 行 | ✅ |
| Scenario Outline 的 Examples 列头唯一 | ✅ |
| 异常路径每个单独一个 Scenario | ✅ |

如果自检不通过，**就地修正后再输出**。

### Step 5 — 输出格式

````markdown
# 输出以下内容 — 可直接保存为 .feature 文件

```gherkin
<生成的 Gherkin 内容>
```
````

## 使用示例

### 输入（需求描述）

> 用户注册功能：
> 1. 用户填写邮箱和密码，点击注册
> 2. 邮箱不能重复，密码至少 8 位
> 3. 注册成功后发送验证邮件
> 4. 邮箱已存在时提示"邮箱已被注册"
> 5. 密码太短时提示"密码至少 8 位"

### 输出

```gherkin
@P0
Feature: 用户注册
  新用户通过邮箱和密码注册账号，注册成功后需验证邮箱

  Background:
    Given 注册页面已打开
      And 注册 API 端点 /api/auth/register 可用

  Scenario: 用户成功注册
    Given 数据库中不存在邮箱 "alice@example.com"
    When 用户填写邮箱 "alice@example.com" 和密码 "SecureP@ss123" 并点击注册
    Then 返回 HTTP 201，响应体包含 { "user_id": "<auto-generated>", "email": "alice@example.com", "status": "UNVERIFIED" }
      And 发送验证邮件到 "alice@example.com"
      And 数据库 users 表新增 1 行，email="alice@example.com", status=UNVERIFIED

  Scenario: 重复邮箱注册被拒绝
    Given 数据库已存在邮箱 "bob@example.com"
    When 用户填写邮箱 "bob@example.com" 和密码 "SecureP@ss123" 并点击注册
    Then 返回 HTTP 409，错误码 EMAIL_ALREADY_EXISTS
      And 错误消息为 "邮箱已被注册"
      And 不发送验证邮件

  Scenario Outline: 密码长度不足被拒绝
    Given 数据库中不存在邮箱 "test@example.com"
    When 用户填写邮箱 "test@example.com" 和密码 "<password>" 并点击注册
    Then 返回 HTTP 400，错误码 PASSWORD_TOO_SHORT
      And 错误消息为 "密码至少 8 位"
      And 不发送验证邮件

    Examples:
      | password | 说明       |
      | 1234567  | 7位数字    |
      | abc      | 3位字母    |
      | P@1      | 含特殊字符但仅3位 |
```

## 多语言支持

Gherkin 支持 70+ 种语言的本地化关键字。如果用户的输入语言是中文、日文等非英语语言，可使用对应的本地化关键字：

**中文关键字对照**：

| 英文 | 中文 |
|------|------|
| `Feature` | `功能` |
| `Rule` | `规则` |
| `Scenario` | `场景` |
| `Scenario Outline` | `场景大纲` |
| `Examples` | `例子` |
| `Background` | `背景` |
| `Given` | `假设` / `假如` / `前提` |
| `When` | `当` |
| `Then` | `那么` |
| `And` | `而且` / `并且` |
| `But` | `但是` |

使用非英语关键字时，在文件首行添加 `# language: <code>`：

```gherkin
# language: zh-CN
功能: 用户注册

  场景: 用户成功注册
    假如 注册页面已打开
    当 用户填写邮箱 "alice@example.com" 和密码 "SecureP@ss123" 并点击注册
    那么 返回 HTTP 201
```

**默认行为**：输出英文关键字。用户指定语言时切换为对应本地化关键字。

## 与 Shadow 管线的关系

| 场景 | 关系 |
|------|------|
| 独立使用（非 Shadow 项目） | 直接输出 Gherkin，无需 `.shadow/` 目录 |
| 嵌入 Shadow L2 | 产出存入 `.shadow/L2-e2e/`，标签遵循 Shadow 约定（`@covers-RXX`、`@covers-BXX-NYY`、`@dimension-N`） |
| 嵌入 Shadow L1.5 | 产出 API 契约场景、质量属性场景 |
| 嵌入 Shadow L6 | 产出部署验证级精简场景 |

在 Shadow 管线中使用时，自动附加 Shadow 标签约定（参见 `skills/shadow-l2-e2e/references/gherkin-guide.md`）。

## 关键约束

1. **只输出 Gherkin** — 不生成测试代码、不生成 step definitions
2. **不编造需求** — 缺少信息时标注 `# inferred` 而非自行假设
3. **异常路径必须独立** — 每个异常情况一个 Scenario，不混入正常路径
4. **断言可验证** — Then 中的断言必须是可以通过 UI/API/DB 观测的值
5. **单 When 原则** — 每个 Scenario 原则上只有 1 个 When；如果需要多个 When-Then 对，在注释中说明原因
