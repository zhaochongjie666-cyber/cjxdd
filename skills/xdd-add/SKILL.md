# xdd-add — Architecture Description Skill

## 使用场景

当用户要求编写、优化、审阅或补全 ADD / Architecture Description / 架构设计说明书时，使用本 skill。

ADD 不重复 BDD 的业务流程，不替代组件拓扑图。ADD 的核心目标是回答：

- 系统如何启动、关闭、恢复？
- 状态如何流转，谁有权推进状态？
- 异常发生时如何自愈、重试、降级或停止推进？
- 并发、资源、幂等、一致性如何保证？
- 运维如何通过日志、指标、探针和状态字段排障？

## 输入对齐要求

生成 ADD 前，优先对齐以下来源：

1. `project.flow.mermaid`
   - 组件名称
   - 协议名称
   - 外部依赖
   - 数据流向

2. `.xdd/bdd`
   - 业务术语
   - 用户动作
   - 领域状态
   - 触发条件

3. 当前代码或用户提供材料
   - 文件路径
   - 服务入口
   - 后台循环
   - 数据模型
   - 状态字段
   - 错误码 / 异常类型

文档中出现的组件名、协议名、核心状态名、字段名必须与以上来源保持一致。未知内容必须标注为"待确认"，不要编造。


## 强制原则
使用大白话+伪代码流程，避免抽象术语和模糊概念。ADD 的目标是让架构设计对所有相关人员（开发、测试、运维、产品）都清晰可见，并且能够指导实现和排障。

1. 禁止纯功能堆砌

   不要复述"用户点击什么、系统创建什么"这类 BDD 内容。必须描述非功能性设计：幂等、一致性、恢复、并发、限流、资源隔离、优雅关闭、可观测性。

2. 禁止抽象空话

   不写"高性能、高可用、稳定可靠"这类无战术表达。必须写成可验证设计，例如：
   - 每 5s 扫描一次
   - 使用 CAS 条件更新
   - 使用 attempt_id 防旧写覆盖
   - 使用 TTL lease 防资源泄漏
   - SIGTERM 后 readiness 返回 503

3. 必须包含状态机

   每份 ADD 必须包含 Mermaid `stateDiagram-v2`，并说明：
   - 状态含义
   - 状态推进方
   - 推进条件
   - 终态
   - 非法状态覆盖防御

4. 必须包含核心时序图

   每份 ADD 必须包含至少一个 Mermaid `sequenceDiagram`，覆盖主链路从入口到终态。

5. 必须包含启动与关闭序列

   需要明确：
   - 初始化顺序
   - 后台循环启动顺序
   - readiness 何时开放
   - SIGTERM 后如何阻断流量
   - 当前事务如何完成
   - 超时后如何恢复

6. 必须包含排障锚点

   ADD 必须能指导线上排障，至少写清：
   - 查哪个状态字段
   - 查哪个 runtime_ref / trace_id / attempt_id
   - 查哪些日志
   - 查哪些外部依赖
   - 哪些状态代表可自动恢复，哪些需要人工介入

## 模版 

```markdown
# [系统名称] 架构设计说明书（ADD）
# 系统名 / 模块名架构说明

## 1. 一句话定位
这个系统解决什么问题，不解决什么问题。

## 2. 背景与目标
为什么需要它。
核心质量目标：可靠性、性能、成本、可观测性、可维护性等。

## 3. 总体架构
一张分层图或组件图。
每层只讲职责、边界、依赖关系，不急着讲函数细节。

## 4. 核心对象与数据模型
最重要的实体是什么。
例如 Job、Task、Attempt、Worker、Allocation。
每个对象说明：谁创建、谁更新、生命周期、关键字段。

## 5. 主流程
讲清楚主路径：
- 创建流程
- 调度流程
- 执行与监控流程
- 结束与结果归档流程

## 6. 状态机
列出状态、合法流转、谁能推进状态、推进条件。
这是调度类系统最重要的部分。

## 7. 失败模型与恢复策略
不要只写 happy path。
要写：
- 外部依赖挂了怎么办
- 进程重启怎么办
- 重复回调怎么办
- 任务丢了怎么办
- 日志延迟怎么办
- 资源泄漏怎么办

## 8. 并发与一致性设计
讲清楚哪些地方可能竞争，以及用什么挡：
- attempt_id
- DB 条件更新
- 锁
- 幂等键
- reconcile
- 乐观并发控制

## 9. 可观测性与排障
出问题时看哪些字段、日志、指标、链路。
最好直接给"排障清单"。

## 10. 关键决策与取舍
为什么这么设计。
哪些方案被放弃，为什么。
这里是架构文档的灵魂，不然文档只是代码导游。

## 11. 风险与后续演进
当前已知短板。
未来扩展方向。
哪些地方不要轻易改。
```
