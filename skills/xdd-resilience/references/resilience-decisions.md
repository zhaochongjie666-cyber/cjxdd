# 韧性设计决策 — 怎么排优先级、选兜底、定混沌范围

> 本文件是 `xdd-resilience` 的深度参考。SKILL.md 列了"8 维度失败模式 + 10 兜底模式 + FMEA 字段"（**有什么**），这里讲**怎么选**：从一堆失败模式里排优先级、给每个选对兜底、定混沌该测哪些。
> 配合 SKILL.md（FMEA 发散）+ `xdd-gherkin-plus`（混沌 Gherkin 语法）。

---

## 1. 失败模式排优先级（FMEA 之后，资源有限不能全兜）

发散出的失败模式常有 20-50 条，不可能全兜（成本爆炸）。按**爆炸半径 × 发生概率**排优先级：

| 爆炸半径 \ 发生概率 | 高频 | 低频 |
|--------------------|------|------|
| **大**（核心链路瘫痪/数据错）| 🔴 **P0 必兜** | 🟠 **P1 应兜** |
| **小**（单功能/可降级）| 🟡 **P2 视情况** | ⚪ **P3 记录即可** |

**爆炸半径判定**（回指 RXX/端点，见 SKILL FMEA 字段）：
- 影响核心业务规则（订单/支付/鉴权）= 大
- 影响数据正确性（写丢失/重复/错乱）= 大
- 只影响非核心功能（统计/通知/展示）= 小
- 有降级路径（挂了用户还能用主要功能）= 小

**发生概率判定**：
- 外部依赖（网络/第三方 API/存储）= 高（迟早会挂）
- 并发/资源竞争 = 中
- 罕见极端（地域级故障/双主）= 低

> **P0 必兜，P1 应兜，P2 量力，P3 写进 failure-modes.md 记录就行（不兜但要知情）**。别试图兜所有——P3 全兜是过度工程。

## 2. 兜底模式怎么选（SKILL 的 10 模式，按失败类型匹配）

SKILL.md 列了 10（大项目 12）兜底模式。选哪个，按**失败类型**匹配：

| 失败类型 | 选什么兜底 | 为什么 |
|---------|-----------|--------|
| 下游服务慢/挂（同步调用）| **熔断 Circuit Breaker** | 快速失败，防止级联雪崩 |
| 核心功能依赖挂但要有兜底结果 | **降级 Degradation** | 返回缓存/默认值/只读模式 |
| 写操作可能重复（网络重试）| **幂等 Idempotency** | 重复请求不产生副作用 |
| 跨系统最终一致 | **业务对账 Reconciliation** | 定时比对修复差异 |
| 资源耗尽（连接/线程/内存）| **限流 + 背压** | 拒绝超载请求保系统活 |
| 进程崩溃/重启 | **健康检查 + 重启 + 状态恢复** | 自愈 |
| 消息丢失/重复 | **死信队列 + 幂等消费** | 不丢消息，重复不致错 |
| 外部调用必成功 | **重试 + 指数退避** | 临时故障自愈 |

**选兜底决策法**：
1. 这条失败**能避免吗**？（如加输入校验避免非法数据）→ 避免 > 兜底
2. 避免不了，**失败后系统能继续跑吗**？能 → 降级；不能 → 熔断/重试
3. **数据会错吗**？会 → 幂等 + 对账
4. 选定后，在 failsafe-design.md 标 `@failure-mode-FXX` 指向它兜的失败模式 + **实现位置**（哪个模块/文件）

> **常见错误**：所有失败都用"重试"兜。重试只对**临时故障**有效，对"数据已错""逻辑已坏"重试只会放大错误。永久性失败要熔断/降级，不是重试。

## 3. 混沌该测哪些（不是所有 P0 都测，测高价值）

混沌测试成本高（要注入故障、验系统反应）。不是每个兜底都做混沌——**选"兜底错了后果最重 + 容易验证"的**：

**优先做混沌的**：
- P0 失败模式的兜底（挂了损失最大，必须验真能兜住）
- 兜底逻辑复杂（对账/补偿/状态恢复——容易写错，要实测）
- 依赖外部系统的兜底（真实故障最难预测）

**不必做混沌的**：
- P3 失败模式（记录了就行）
- 简单兜底（输入校验/基础幂等——逻辑直白，单测覆盖即可）
- 纯展示降级（挂了只是少个图表，不值得混沌）

**混沌 Gherkin 要可执行**（见 SKILL §4）：When 必须是**具体注入命令**（`kill -9 进程` / `iptables 断网` / `数据库停 30s`），Then 验**系统实际反应**（熔断器打开 / 降级返回缓存 / 告警触发 / 恢复后正常），不是"应该有韧性"这种空话。

---

## 4. 兜底 vs 避免 vs 接受（三条路，别只会兜）

面对一个失败模式，有三条路，按顺序选：

```
失败模式 → 能避免吗？
           ├─ 能（加校验/约束/前置检查）→ 避免（最优，根本不发生）
           └─ 不能 → 后果能接受吗？（展示降级/可手动修）
                     ├─ 能且成本低 → 接受（记 failure-modes，不兜）
                     └─ 不能 → 兜底（按 §2 选模式）
```

**避免 > 兜底 > 接受**。能避免的失败别兜（多此一举）；后果可接受的不兜（省成本）；兜底是最后的手段。很多团队的错是"跳过避免，直接兜"——本可加个约束就解决的问题，搞了套复杂的重试+对账。

---

## 5. 和上下游的衔接

- **FMEA 的爆炸半径** 回指 spec 的 RXX + architecture 的端点（`@failure-mode-FXX` + `@covers-RXX`）—— 失败模式不是凭空想的，是"这条规则/端点挂了会怎样"
- **兜底的实现位置** 回指 architecture 的模块（`@failure-mode-FXX` + 实现位置）—— 兜底要落到具体模块，plan 据此拆 task
- **混沌 Gherkin** `@covers-RXX` 回指 spec —— 验的是"规则在故障下还成立吗"
- **failure-modes.md 的运维视图种子** ← architecture 的 ODD 失败模型（SKILL §1 读骨架）

## 6. 自检（韧性设计决策质量）

```
□ 失败模式按 爆炸半径×概率 排了优先级（P0/P1/P2/P3），没试图全兜？
□ 每条 P0/P1 选了对的兜底模式（按失败类型匹配，不是无脑重试）？
□ 先考虑"避免"再"兜底"（能加约束避免的失败别兜）？
□ 混沌只测 P0 + 复杂兜底 + 外部依赖（不是全测）？
□ 混沌 When 是具体注入命令，Then 验实际反应（不是空话）？
□ 兜底都标了 @failure-mode-FXX + 实现位置（能被 plan 拆 task）？
```
