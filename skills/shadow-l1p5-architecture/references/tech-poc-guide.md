# L1.5 技术验证（Tech PoC）指南

## 为什么需要技术验证

L1.5 架构设计选了技术栈，但**选择未必等于能跑**。常见风险：

1. **库版本冲突**：选型时假设的版本在生产环境装不上
2. **性能不达标**：本地 PoC 没压测，线上崩
3. **集成不通畅**：两个库的设计哲学冲突（如同步 vs 异步）
4. **运维不支持**：选了一个团队不会运维的技术
5. **许可证问题**：商用许可没看清

**技术验证 = 在写第一行业务代码前，先用最小代码验证高风险组件真能跑**。

## 哪些组件需要 PoC

### 高风险组件清单

| 风险等级 | 组件类型 | 必须 PoC |
|---------|---------|---------|
| 🔴 高 | 新技术栈（团队没用过） | 必须 |
| 🔴 高 | 复杂中间件（消息队列、分布式锁、调度器） | 必须 |
| 🔴 高 | 第三方 SaaS API（支付、短信、邮件） | 必须 |
| 🟡 中 | 主流框架（FastAPI、Spring Boot、React） | 可选，但建议 |
| 🟡 中 | 数据库（PostgreSQL、Redis、MongoDB） | 必验证连通性，可选压测 |
| 🟢 低 | 标准库、工具库（loguru、axios） | 不需要 |

### 风险评估问题

对每个技术选型问：

```
1. 团队是否有生产经验？
2. 是否有成熟的中文/英文文档？
3. 社区活跃度？最后 release 是什么时候？
4. 许可证是否允许商用？
5. 性能基准（官方 benchmark）是否符合预期？
6. 与现有技术栈是否冲突？
7. 故障模式是否已知？运维文档齐全吗？
```

> 任何一个回答「不」或「不知道」，就该 PoC。

## PoC 范围

**最小可行 PoC（不追求生产）**：

```
目标：证明「这个组件能装上、跑起来、满足最基本的功能」
不做：性能压测、错误处理、监控、安全
时长：1-4 小时
代码量：< 200 行
```

**PoC 必须包含**：

1. 安装（`package.json` / `pyproject.toml` / `Dockerfile`）
2. 最小可运行代码（Hello World 级别）
3. 一个真实业务场景的最小复现（如发一条消息、跑一个事务）
4. 失败时的错误信息

## 常见组件的 PoC 验证清单

### 消息队列（Kafka / RabbitMQ / Redis Streams / Nomad）

```markdown
- [ ] 生产/消费一条消息（同步）
- [ ] 消费失败时消息不丢
- [ ] 消费失败重试（带退避）
- [ ] 消费者扩缩容（不停服）
- [ ] 消息顺序保证（如需要）
- [ ] 积压监控可见
- [ ] 消息不重复（如需要）
```

### 分布式锁（Redis / etcd / Zookeeper）

```markdown
- [ ] 加锁/解锁
- [ ] 锁超时自动释放
- [ ] 锁竞争时阻塞/失败符合预期
- [ ] 锁的所有者宕机时锁能释放
- [ ] 时钟漂移场景
```

### 调度器（Nomad / K8s CronJob / Celery Beat / Quartz）

```markdown
- [ ] 触发一个 cron 任务
- [ ] 多实例同时跑不会重复执行
- [ ] 任务执行时间 > 间隔会怎样
- [ ] 任务失败重试
- [ ] 任务超时处理
- [ ] 任务积压处理
```

### 第三方 SaaS API（支付 / 短信 / 邮件 / OAuth）

```markdown
- [ ] Sandbox 环境连通
- [ ] 鉴权方式
- [ ] 主要功能调用
- [ ] 错误码体系
- [ ] 限流策略
- [ ] Webhook 接收（如有）
- [ ] 生产环境切换流程
- [ ] 沙箱和生产环境的差异
```

### 数据库（PostgreSQL / MySQL / MongoDB）

```markdown
- [ ] 客户端连通
- [ ] 基本 CRUD
- [ ] 事务
- [ ] 索引生效
- [ ] 连接池配置
- [ ] 备份/恢复
- [ ] 主从同步
- [ ] 大表操作（DDL）
```

## PoC 完成后

PoC 报告产出后：

1. **更新 L1.5 architecture.md**：在技术栈决策段加 `@poc: .shadow/L1.5-architecture/poc/{component}.md` 引用
2. **触发 L3**：PoC 发现的限制/坑转成失败模式
3. **失败回退**：PoC 不通过 → 回 L1.5 重新选型

## 反模式

❌ **「官方文档说能跑」** = 跳过 PoC：文档说的不等于你环境能跑
❌ **「我用 Hello World 跑过了」** = 跳过完整场景：Hello World 不代表业务可用
❌ **「先写业务代码，遇到问题再 PoC」**：技术选型错了再返工成本 10x
❌ **「PoC 写 1 个月」**：PoC 应该 < 4 小时，超时就该放弃
❌ **「PoC 代码直接当生产代码」**：PoC 代码无错误处理、无监控，不能直接用

## 工具

- `.shadow/L1.5-architecture/poc/{component}.md` — PoC 报告

## 与其他层的关系

```
L1.5 architecture 选型
  ↓
L1.5 PoC 验证（高风险组件）
  ↓
L3 失败模式发散（从 PoC 发现的坑+架构边界）
  ↓
L2 e2e 场景（验证 PoC 过的组件集成）
  ↓
L5 impl 实际使用（基于 PoC 经验）
```
