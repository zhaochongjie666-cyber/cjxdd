# 任务拆解法 — 怎么拆 task、排依赖、判 plan 质量

> 本文件是 `xdd-plan` 的深度参考。SKILL.md 讲了"一个 task = 一个行为路径 + 粒度表（3/5/7 步）+ DAG 结构"（**结构规则**），这里讲**怎么判断**：一个 task 该拆还是合、依赖怎么排不乱、plan 写完怎么自查是不是好计划。
> 拆任务是最考经验的一步——拆太碎执行啰嗦，拆太粗 TDD 失效，依赖排错会卡死执行。

---

## 1. 一个 task 该拆还是合（粒度判断）

SKILL.md 给了"3/5/7 步 + 超 7 步必拆"的硬规则。这里是**边界判断**：

**该拆（task 太大）的信号**：
- 一个 task 实现了**多条 RXX**（除非是同一约束的正反面）→ 拆成每 task 一条 RXX
- 一个 task 跨**多个组件层**（前端+后端+DB 一起改）→ 按层/按行为路径拆
- 估超过 7 步 / 单 task 写不完一次（超 30 分钟）→ 拆
- task 里出现"并且"（"实现登录**并且**记住我"）→ 拆成两个

**该合（task 太碎）的信号**：
- 两个 task 总是**一起做、不单独有价值**（"建表"+"写 CRUD"通常是合一的）→ 合
- 一个 task 只有 1-2 步、没独立验收意义 → 合到相关 task
- 两个 task 是**同一 RXX 的正反两面**（登录成功 + 登录失败）→ 可合（一个 task 多 Scenario），或保持两个但标紧密依赖

**粒度自检**：task 列表读一遍，每个能独立 TDD（写测试→实现→过）+ 独立 commit 吗？能 = 粒度对。

> **常见错误**：按"组件"拆（一个 task 建数据库、一个建 API、一个建前端）。错——按**行为路径**拆（"用户能登录"这个行为，横跨 DB+API，是一个 task；测试验的是"登录成功"这个行为，不是"建了张表"）。按组件拆的 task 没有可验收的行为。

---

## 2. 依赖怎么排（DAG 不出错）

依赖决定执行顺序。排错 = 卡死（等一个永远不会完成的依赖）。

**依赖来源**（什么情况标 Depends on）：
| 情况 | 依赖 |
|------|------|
| task B 用 task A 建的数据结构 | B depends on A |
| task B 调 task A 建的接口 | B depends on A |
| task B 验收需要 task A 的功能存在 | B depends on A |
| 两个 task 完全独立 | 无依赖，可并行 |

**排依赖的纪律**：
- **只标真依赖**（数据/接口/验收前置），别因为"感觉应该先做"就加依赖（会制造假的串行）
- **依赖只指已有的 task**（不能 depends on 一个不存在的 task）
- **检查无环**：A→B→C→A 是死锁，plan 头部的依赖表画出来一眼能看出环
- **首批 ready**：至少有一个无依赖的 task（否则全卡住，没有起点）

**验证 DAG 合法**：
```
拓扑排序能跑通（有起点，无环）= 合法
有环 / 无起点 = 非法，回去改依赖
```

> **常见错误**：把所有 task 串成一条链（T1→T2→T3→...）"保险"。错——抹杀了可并行的 task，执行变慢。只有真有数据/接口依赖才串，独立的让它们并行。

## 3. RXX → Task 映射（每条规则有 task 实现）

plan 的核心职责是把 spec 的 RXX 规则**完整覆盖**成 task。映射检查：

- **每条 RXX 至少有一个 task 实现它**（task 的 `回指 RXX` 字段标出来）
- **没有 task 指向不存在的 RXX**（回指的 RXX 在 spec rules.md 里得有）
- **RXX 覆盖追踪表**（plan 头部）每条 RXX 有对应 task

**映射自检**：
```
spec 的 RXX 数 = N
plan 里 回指 RXX 覆盖的规则数 = M
M == N ? → 全覆盖 ✅
M < N ? → 有规则没拆 task，漏了（回去补 task）
M > N ? → 有 task 指向不存在的规则，标错（查回指）
```

> 这是下游 execute `@implements` + verify 计数对照的源头。plan 漏一条 RXX，下游整条链就缺一块。

## 4. plan 质量自检（写完逐项过）

好 plan 的特征（execute 能照着做，不卡壳）：

| 维度 | 好计划 | 坏计划 |
|------|--------|--------|
| 粒度 | 每 task 一个行为路径，3-7 步 | 按组件拆 / 步数失控 |
| 依赖 | 真依赖才标，无环，有起点 | 全串成链 / 有环 / 无起点 |
| RXX 覆盖 | 每条 RXX 有 task，无悬空 | 漏规则 / 指错规则 |
| 具体性 | 每步写清改哪个文件、写什么、验什么 | "实现登录功能"（太空）|
| 无占位符 | 真步骤，无 TODO/待定 | 占位符伪装完成 |
| 文件结构 | 列清改哪些文件（分解决策锚）| 不知改哪 |

**写完 plan 自检**（SKILL 自检段的补充）：
```
□ 按"行为路径"拆（非组件），每 task 3-7 步、超 7 拆？
□ 依赖只标真依赖，DAG 无环有起点，独立的并行？
□ RXX 全覆盖（M==N），无悬空回指？
□ 每步具体到文件 + 动作 + 验证，无占位符？
□ execute 照着能做（不用猜、不用补设计）？
```

---

## 5. 和上下游衔接

- **上游**：plan 读 spec 的 RXX + architecture 的端点/文件清单 + wire 的页面 + resilience 的兜底约束（SKILL 输入对齐段）
- **下游**：execute 按 task 顺序 TDD，每 task `@implements` 回指 RXX；verify 按 RXX 覆盖验收
- **回溯**：plan task 的 `回指 RXX` 是 execute→verify 追溯链的桥梁。plan 这步漏/错，下游全乱

> plan 是**桥**——设计层（RXX/架构/页面）和代码层（execute/verify）之间。plan 质量直接决定代码层能不能跑通、可不可追溯。
