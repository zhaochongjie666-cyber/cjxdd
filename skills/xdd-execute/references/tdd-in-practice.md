# TDD 落地实操 + 反 sham 手法

> 本文件是 `xdd-execute` 的深度参考。SKILL.md 讲了 TDD 流程框架（红绿重构、Pre-write Signoff、反 sham 底线），这里讲**实操怎么落地**：测试怎么写才好、红绿重构怎么真的转、`@implements` 落在哪、sham 的常见手法和对策。
> 这是代码层最易翻车的地方——TDD 写成"先写测试再写代码"的形式主义，或 sham 伪装 GREEN，都是常见坑。

---

## 1. 测试怎么写才"好"（不是写了就行）

TDD 的测试是**验收契约**，不是覆盖率凑数。好测试三特征：

| 特征 | 说明 | 反例 |
|------|------|------|
| **能失败** | 代码写错时测试必须红。不会失败的测试 = 没价值 | 测试只检查"函数返回非 null"，永远过 |
| **验行为非实现** | 测"做了什么"，不测"怎么做"（不绑死实现细节）| 测私有方法/测内部数据结构/测调用次数 |
| **断言具体** | Then 写具体可观察值（状态/返回/数据变化），不是"成功" | `assert result != None` 而非 `assert result.status == 'created'` |

**写测试的顺序（TDD 红→绿）**：
1. 想清楚这条 RXX 规则的**可观察结果**是什么（接口返回？数据变化？状态转移？）
2. 写**一个**失败测试（最小、最具体的断言）
3. 跑——确认它**真的红了**（红了才证明测试有效；直接绿 = 测试有 bug 或测错了东西）
4. 写**最小实现**让它绿（不多写）
5. 重构（清理，保持绿）
6. 下一个断言/异常路径，重复

> **关键：第 3 步确认红**。很多人跳过这步，结果测试从没失败过——那这个测试可能根本没在测你想测的东西。

## 2. 红绿重构怎么真的转（不是口号）

| 阶段 | 做什么 | 常见错误 |
|------|--------|---------|
| 🔴 红 | 写**一个**失败测试，跑，确认它因"功能没实现"而失败 | 一次写 10 个测试再实现（失去小步反馈）；测试因 import 错/语法错红（那是测试 bug，不是功能未实现）|
| 🟢 绿 | 写**最小**代码让测试过。丑也行、重复也行，先绿 | 边实现边加"顺便"功能；写超过让测试过的代码（YAGNI）|
| 🔵 重构 | 测试保持绿的前提下，清理代码（去重/命名/抽函数）| 重构时跑测试发现红，又回去改实现（说明绿阶段代码太脆）|

**小回环原则**：红绿重构是**分钟级**的循环，不是"写完所有测试再实现"。一个断言一个循环。task 内多个 Scenario = 多个小回环。

> 失败（测试红）→ 修**代码**让它绿 → 再跑。这是修代码，**不算"卡住 3 试"**（3 试是指同一处连续 3 次修不对）。但如果反复修不对，说明 plan 的步骤有问题，才触发 rollback。

## 3. `@implements RXX` 落在哪（追溯标签的落点）

`@implements RXX` 是代码回指规则的标签。**落点规则**：

| 代码形态 | @implements 落哪 |
|---------|-----------------|
| API 端点（handler）| 端点函数注释，标它实现的规则 `// @implements R01` |
| 业务逻辑（service）| 实现 RXX 核心约束的方法注释 |
| 一段代码实现多条规则 | 可标多个 `// @implements R01,R03`（但说明这方法职责重，考虑拆）|
| 一条规则散在多处 | 每处都标同一个 RXX（grep 能聚合）|

**verify 怎么用它**（见 verify 4 维审计）：`grep @implements` 计数 ≥ spec 的 RXX 数。所以：
- **每条 RXX 至少有一处 @implements**（否则 verify 判规则没实现）
- **别标错规则**（@implements R03 实际实现的是 R05 的逻辑 = 追溯链错乱）

> 落 `@implements` 的时机：绿阶段（实现完一个断言）就标，不要等全做完再补（会漏）。commit message 也带 RXX（双保险）。

## 4. sham 的常见手法（对照自检，别犯）

sham = 用假实现伪装 GREEN。SKILL.md 列了底线（无存根/无假实现/跑通有证据），这里是**具体手法识别**：

| sham 手法 | 长什么样 | 为什么是 sham | 正确做法 |
|-----------|---------|--------------|---------|
| 存根返回 | `def login(): return {"token": "fake"}` | 硬编码结果，没真逻辑 | 实现真鉴权逻辑 |
| InMemoryRepo | 数据存内存 dict，重启没 | 假装持久化 | 接真 DB + 迁移 |
| 硬编码用户 | `current_user = User(id=1)` | 跳过认证 | 从认证上下文取 |
| mock 掉被测对象 | 测 service 时 mock service 本身 | 测了 mock 不是代码 | mock 依赖（DB/外部），不 mock 被测对象 |
| 断言放水 | `assert response.status_code in [200,201]` 放宽 | 掩盖实际不对 | 断言精确值 |
| 测试不触发逻辑 | 测试调了个空函数 | 形式上 GREEN | 测试走完整路径 |
| 只测 happy path | 只测正常流程 | 异常路径全没覆盖 | 每个 Scenario（含异常）都有测试 |

**自检 sham 的硬办法**：
1. `bash skills/xdd-execute/scripts/no-stub-check.sh <文件>` —— 扫存根关键词（pass/TODO/None/NotImplemented/InMemory/mock），零命中才过
2. **重启还在吗**：写→查→**重启服务**→查，数据还在 = 真持久化；重启没了 = InMemory sham
3. **真跑有证据**：curl 真请求拿真响应，不是"应该能跑"

## 5. task 内卡住的判断（别在错的层面硬扛）

| 情况 | 说明 | 怎么办 |
|------|------|--------|
| 测试红，改代码能绿 | 正常 TDD 循环 | 改代码（不计"卡住"）|
| 同一处改 3 次还不绿 | 代码层硬扛无意义 | rollback：回 plan 看步骤对不对，或更上 spec/design 找根因 |
| 测试写不出（不知道断言什么）| 规则没想清 | 回 spec 看 RXX 的 Then，或回 plan 看 task 的验收 |
| 依赖的 task 没完成 | 不能跑 | 不该开始这个 task，回 DAG 看依赖 |

> 核心心法（SKILL 也强调）：**3 试没过别在代码层反复修**——多半是 plan 步骤错或规则没想清，回上游找根因，不在错的层面硬扛。

## 6. 自检（TDD 落地质量）

```
□ 每个测试都确认过"真的红过"（不是一开始就绿）？
□ 测试验行为非实现（没绑死私有方法/内部结构）？
□ Then 断言具体（状态码/字段/数据变化），不是"成功"？
□ 红绿重构是分钟级小回环（一个断言一循环）？
□ 每条 RXX 有 @implements 落点（绿阶段就标，不等补）？
□ no-stub-check.sh 零命中 + 重启数据还在 + curl 真响应（三重反 sham）？
□ 异常路径 Scenario 也有测试（不只 happy path）？
```
