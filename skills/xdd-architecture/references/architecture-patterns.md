> 人可直接读(速查),AI 按需 load(框架资产)。一份文档两个用途。

## 为什么要这个文件

没有这个文件之前,做任何产品架构层只会默认套 4 层分层(`Presentation → Application → Domain → Infrastructure`)——哪怕场景明明该用事件总线或 CQRS。本文件给出「**先按质量属性选模式**」的决策依据,让架构选择有据可查、可追溯(每个选择标 `@intent`,跟框架的锚习惯一致)。

## 决策矩阵:质量属性 → 模式

先把 ADD 产出的 3-5 个质量属性场景摆出来,按「**最该满足的那个质量属性**」查行,再按上下文查列。

| 主导质量属性 | 小项目 / 单体 | 有状态 + 高可用 | 数据流 / ETL | 高并发突发 | 解耦 + 演进 |
|---|---|---|---|---|---|
| **可修改性**(需求常变) | [分层](#1-分层--layered) | [六边形](#14-六边形端口适配器--hexagonal整洁架构洋葱架构变体并入) | [管道-过滤器](#4-管道-过滤器--pipe-filter) | — | [微服务](#11-微服务--microservices) |
| **性能**(P95/吞吐) | [分层](#1-分层--layered) | [Primary-Replica](#3-主-从--primary-replica旧称-master-slave) | [管道-过滤器](#4-管道-过滤器--pipe-filter) | [Space-based](#15-space-based--基于空间) | [CQRS](#12-cqrs命令查询职责分离) |
| **可用性**(SLA/零停机) | — | [Primary-Replica](#3-主-从--primary-replica旧称-master-slave) | — | [Space-based](#15-space-based--基于空间) | [事件总线](#7-事件总线--event-bus) + [事件溯源](#13-事件溯源--event-sourcing) |
| **可伸缩性**(水平扩展) | [客户端-服务器](#2-客户端-服务器--client-server) | [Primary-Replica](#3-主-从--primary-replica旧称-master-slave) | — | [Space-based](#15-space-based--基于空间) / [P2P](#6-对等--peer-to-peer) | [微服务](#11-微服务--microservices) |
| **安全性**(隔离/合规) | [分层](#1-分层--layered)(+DMZ) | — | — | — | [六边形](#14-六边形端口适配器--hexagonal整洁架构洋葱架构变体并入)(防腐层) |

**怎么用**:① 列出本项目的质量属性场景(已在 ADD 第 1 步写好);② 找到「最不能妥协」的那一行的列;③ 读推荐模式的「适用/不适用」,确认上下文匹配;④ 把选择写进 architecture.md 的技术决策,标 `@intent`(背景→选项→选了→为什么)。**多模式组合是常态**——例如「分层单体 + 事件总线做异步」很常见。

---

## 选模式三步法

```
1. 查决策矩阵 → 候选 2-3 个模式
2. 读候选模式的「适用 / 不适用」→ 砍掉上下文不符的
3. 在 architecture.md 写 @intent:背景→选项→选了→为什么
```

**禁区**:不要因为「分层最熟」就直接套。分层是**模式之一**,不是默认答案。先查矩阵再说。

## 10 个经典架构模式

每条模式统一模板:**一句话定义 → 结构 → 适用(质量属性标签)→ 优缺点 → 不适用 → 落到 xdd 哪层**。

---

### 1. 分层 / Layered

`@quality-attr:可修改性 / 安全 / 可测试性`

**一句话**:把系统横向切成若干层,每层只依赖下一层,职责单向流动。

**结构**:

```
┌─────────────────────────┐
│ Presentation (UI+API)   │  ← 对外:HTTP/页面
├─────────────────────────┤
│ Application (用例编排)   │  ← 事务边界/用例
├─────────────────────────┤
│ Domain (业务规则)        │  ← 核心:RXX 规则落这里
├─────────────────────────┤
│ Infrastructure (DB/MQ)  │  ← 外部世界
└─────────────────────────┘
       依赖方向:上 → 下
```

**适用**:绝大多数业务系统、CRUD 应用、内部管理系统。**最稳的起点**——团队熟、改一层不波及别层。

**优点**:职责清晰;可替换某层实现(如换 DB 只动 Infrastructure);易测试(每层可 mock 下层)。
**缺点**:简单请求穿多层有性能开销;层容易泄漏(领域层反向依赖 UI 框架);层数多了过度工程。

**不适用**:数据流式处理(看管道-过滤器);无中心协调的协作(看 P2P);规则/知识不确定(看黑板)。

**落到 xdd**:这是 architecture.md「规则传导矩阵」的默认载体——每条 RXX 规则映射到 Application/Domain 的某个文件。**但记住:这是默认,不是唯一**。

---

### 2. 客户端-服务器 / Client-Server

`@quality-attr:可伸缩性 / 可用性`

**一句话**:客户端发起请求,服务器响应;职责按「请求方/服务方」切分,可各自独立扩展。

**结构**:

```
[N 个客户端]  ──请求/响应──▶  [1 个服务器(可水平扩展成集群)]
   (瘦)                          (胖:业务+数据)
```

**适用**:几乎所有 Web/API 系统、移动 App 后端、SaaS。这是分层架构的**部署形态**。

**优点**:职责天然分离;客户端可独立演进;服务器集中管控数据/安全。
**缺点**:服务器是单点(需做 HA);网络是隐式依赖(断网=不可用)。

**不适用**:纯离线协作(看 P2P);实时高吞吐数据流(看管道-过滤器)。

**落到 xdd**:xdd 的 API 端点清单(architecture.md 第 7 步)就是这个模式的契约表——客户端=前端(wire 产出的页面),服务器=后端分层。

---

### 3. 主-从 / Primary-Replica(旧称 Master-Slave)

`@quality-attr:可用性 / 性能(读扩展)`

**一句话**:一个 Primary 写,多个 Replica 读;写集中、读分散。

> **命名说明**:旧称 Master-Slave。现代文档逐步改用 Primary-Replica / Leader-Follower,避免历史联想。本库沿用「主-从」中文,技术含义等同 Primary-Replica。

**结构**:

```
        ┌── 写 ──▶ [Primary] ──复制──┐
[客户端]─┤                            ├──▶ [Replica 1] (读)
        └── 读 ──▶ ... ───────────────┼──▶ [Replica 2] (读)
                                      └──▶ [Replica N] (读)
```

**适用**:读多写少的系统(内容站、报表)、数据库高可用、配置分发中心。
**优点**:读吞吐线性扩展;Primary 挂了可提升 Replica(需选主);读写隔离。
**缺点**:复制延迟(最终一致);写仍单点;选主复杂(Split-brain 风险)。

**不适用**:写密集型(瓶颈在 Primary);强一致读(复制延迟破坏线性一致)。

**落到 xdd**:Docker Compose 的 `depends_on: service_healthy` + 多副本服务是这个模式的部署实现;ODD(运维视图)的「失败模型」要写 Primary 挂掉如何提升 Replica。

---

### 4. 管道-过滤器 / Pipe-Filter

`@quality-attr:可修改性 / 性能(吞吐)`

**一句话**:数据流过一串过滤器,每个过滤器独立变换数据,过滤器间只通过数据耦合。

**结构**:

```
[输入]─▶│Filter A│─▶│Filter B│─▶│Filter C│─▶[输出]
         解析       校验        转换
       (每个 filter 独立,可并行/可重排)
```

**适用**:ETL、数据管道、编译器前端、音视频转码、日志处理链。
**优点**:过滤器可独立开发/测试/重用;易加新处理步骤;天然支持并行(不同 filter 跑不同核)。
**缺点**:不适合需要全局状态/交互的;每步数据传递有开销;错误处理跨过滤器难。

**不适用**:交互式 UI、事务型业务逻辑(看分层)、需要即时人决策的(看黑板)。

**落到 xdd**:flow.mermaid 用组件分解体现数据流时,若主链路是「数据变换序列」就该画成管道,而不是分层调用。

---

### 5. 代理 / Broker

`@quality-attr:可修改性(解耦)/ 可伸缩性`

**一句话**:一个中间人(Broker)协调多个对等的服务/组件,彼此不直接知道对方地址。

**结构**:

```
[服务 A]──┐                    ┌──[服务 B]
          ├──▶ [Broker] ──路由──┤
[服务 C]──┘  (注册/发现/转发)    └──[服务 D]
```

**适用**:消息队列(Kafka/RabbitMQ)、微服务 API 网关、SOA、远程调用总线。
**优点**:服务位置透明(可动态增减);请求方与服务方解耦;Broker 可做负载均衡/重试。
**缺点**:Broker 是新单点(需 HA);多一跳延迟;调试难(链路跨进程)。

**不适用**:点对点直连够用的简单场景(过度工程);超低延迟(多一跳不行)。

**落到 xdd**:当 architecture.md 的事件契约(第 8 步)选「消息中间件传递」而非「同步 HTTP」时,实质上就引入了 Broker。event-contract.md 要标清谁是 Broker、重试策略谁定。

---

### 6. 对等 / Peer-to-Peer

`@quality-attr:可伸缩性 / 可用性(去中心)`

**一句话**:无中心服务器,每个节点既是客户端又是服务器,彼此直接协作。

**结构**:

```
    [Peer]──┐  ┌──[Peer]
       │    │  │    │
    [Peer]──┼──┼──[Peer]
       │    │  │    │
    [Peer]──┘  └──[Peer]
    (每个 peer 地位对等,数据/计算分散在全网)
```

**适用**:文件共享(BitTorrent)、区块链、WebRTC 实时通信、分布式计算(SETI@home)。
**优点**:无中心瓶颈/单点;规模越大能力越强(抗伸缩);天然抗审查。
**缺点**:协调复杂(一致性难);信任难(无权威);调试极难;数据一致性弱。

**不适用**:需要强一致/中心管控的业务系统(如交易、账务);团队不熟分布式。

**落到 xdd**:罕见。若选,architecture.md 必须单独写「一致性模型」(Gossip? CRDT? 中本共识?),ODD 的「失败模型」要把「拜占庭节点」「网络分区」列入。

---

### 7. 事件总线 / Event-Bus

`@quality-attr:可修改性(解耦)/ 可用性(异步)`

**一句话**:组件通过发布/订阅事件通信,发布者不认识订阅者,总线负责分发。

**结构**:

```
[组件 A]─发布事件─▶┌─────────────┐─分发给订阅者─▶[组件 B]
[组件 C]─发布事件─▶│  事件总线    │───────────────▶[组件 D]
                   │ (in-proc/MQ)│───────────────▶[组件 E]
                   └─────────────┘
   (发布者不知道谁订阅,订阅者不知道谁发布)
```

**适用**:需要松耦合扩展点的系统、领域事件驱动、UI 组件通信(前端 EventBus)、工作流编排。
**优点**:组件解耦,加新订阅者不改发布者;天然异步,提升响应性;事件可回放。
**缺点**:控制流变隐式(难追踪「这个状态怎么来的」);事件顺序/重复处理复杂;调试难。

**不适用**:强同步语义(如事务内必须完成);事件爆炸难治理。

**落到 xdd**:当 architecture.md 的事件契约决定用「发布订阅」而非「直接调用」时即此模式。**关键纪律**:每个事件必须有 `@flow BXX-NYY`(流程节点)和明确订阅方,否则就成了「隐式散射」——架构自检明确禁止。xdd-resilience 的 `@chaos` 要覆盖「事件丢失/重复/乱序」。

---

### 8. MVC / Model-View-Controller

`@quality-attr:可修改性(UI 层)`

**一句话**:把 UI 密集型应用分成 Model(数据/规则)、View(展示)、Controller(输入调度),三者通过观察者/命令协作。

**结构**:

```
        ┌── 用户操作 ──▶ [Controller] ──修改──▶ [Model]
        │                    │                     │
     [View]◀── 通知变化 ──────┘◀── 查询 ───────────┘
     (View 订阅 Model 变化,Controller 翻译输入)
```

**适用**:有图形界面且交互复杂的系统、Web 框架(Rails/Django/Express MVC)、桌面应用。
**优点**:UI 与业务分离;多 View 共享一个 Model;可独立测试 Model。
**缺点**:纯后端 API 用不上(没有 View);M-V-C 三角依赖容易循环;小项目过度结构。

**不适用**:纯后端服务(看分层)、数据管道(看管道-过滤器)。

**落到 xdd**:这是 [分层](#1-分层--layered) 在 UI 层的细化。前端项目里,xdd-wire 产出的页面组件 ≈ View,调用后端 API ≈ Controller 角色,后端 Domain ≈ Model。纯后端项目跳过。

---

### 9. 黑板 / Blackboard

`@quality-attr:无确定性解法的问题(知识聚合)`

**一句话**:多个独立知识源(KS)围绕一个共享「黑板」(共享数据结构)协作;没有固定控制流,谁有贡献谁就更新黑板。

**结构**:

```
[KS1:视觉]──┐                    ┌──▶[触发 KS2]
[KS2:推理]──┼──读写──▶[黑板]──────┼──▶[触发 KS3]
[KS3:词典]──┘  (共享状态)         └──▶[收敛到解/无解]
   (控制器监视黑板变化,激活合适的 KS)
```

**适用**:AI/专家系统、语音识别、计算机视觉、规则引擎、搜索排序融合。
**优点**:能处理「无确定算法」的开放问题;KS 可增量添加;容错(一个 KS 错不致命)。
**缺点**:不可预测(同样输入可能不同解);难测试/调试;性能不可控(收敛慢)。

**不适用**:有明确流程的业务系统(看分层或管道);对延迟敏感的实时系统。

**落到 xdd**:当 architecture.md 的技术栈涉及 AI 推理/多模型协作时,实质就是黑板模式。要把「黑板数据结构」+「各 KS 触发条件」写进 ODD 的状态机。

---

### 10. 解释器 / Interpreter

`@quality-attr:灵活性(运行时可改规则)`

**一句话**:定义一种「语言/规则」,系统在运行时解释执行它,而非把逻辑硬编码进代码。

**结构**:

```
[规则/脚本]─▶┌───────────┐─执行结果─▶[输出]
             │ 解释器引擎 │
[输入数据]─▶│ (词法/语法/ │
             │  求值器)    │
             └───────────┘
   (规则与引擎分离:改规则不改引擎)
```

**适用**:DSL(领域特定语言)、规则引擎(风控/营销)、配置驱动系统、表达式计算、工作流引擎。
**优点**:终端用户可改规则不动代码;规则集中可审计;引擎复用度高。
**缺点**:性能差(解释比编译慢);语言设计本身是工程;调试工具难做。

**不适用**:性能关键路径(看硬编码);规则少且稳定(直接写代码更简单)。

**落到 xdd**:当 RXX 规则(来自 spec)频繁变且需「不改代码就能改规则」时考虑。架构.md 要在技术栈决策里标「规则引擎 + @intent」,并把规则与引擎的分界写清。

## 5 个现代扩展模式

经典 10 个主要来自 90 年代单机/早期分布式时代。现代云原生/数据密集系统常还需要下面 5 个。

---

### 11. 微服务 / Microservices

`@quality-attr:可修改性(独立演进)/ 可伸缩性(局部扩展)/ 可用性(故障隔离)`

**一句话**:把单体拆成多个独立部署的小服务,每个服务自治(自己的数据+技术栈),通过网络协作。

**结构**:

```
┌─[服务 A]──┐   ┌─[服务 B]──┐   ┌─[服务 C]──┐
│ 自己的DB  │   │ 自己的DB  │   │ 自己的DB  │
│ 独立部署  │◀─┤│ 独立部署  ││─▶│ 独立部署  │
│ API/事件  │   │ API/事件  │   │ API/事件  │
└───────────┘   └───────────┘   └───────────┘
   (服务间通过 API 网关 / 事件总线 / Broker 通信,不共享数据库)
```

**适用**:多团队大型系统、各模块伸缩需求差异大、需要技术栈异构。
**优点**:独立部署/演进/伸缩;故障隔离;团队自治。
**缺点**:分布式复杂度(网络/一致性/追踪);运维成本高(需容器编排 + 服务网格);跨服务事务难。

**不适用**:小团队/小项目(单体分层更简单);强一致跨实体事务;团队没有 DevOps 能力。

**落到 xdd**:多业务线(BXX)天然映射到微服务边界——每条 BXX 可独立成一个服务。aggregate-landscape.md 定义跨服务聚合关系,event-contract.md 定义服务间事件契约。**警告**:不要为了「先进」上微服务,先确认团队规模和运维能力。

---

### 12. CQRS(命令查询职责分离)

`@quality-attr:性能(读写各自优化)/ 可伸缩性`

**一句话**:把「写」(命令,改变状态)和「读」(查询,返回数据)分成两条独立路径,各自用最适合的数据模型/存储。

**结构**:

```
                ┌─[命令端]─▶ 写模型 ──▶ 写库(优化写入)
[客户端]──请求──┤
                └─[查询端]◀─ 读模型 ◀─ 读库(优化查询/投影)
   (写库 → 异步投影 → 读库;两端模型不同)
```

**适用**:读写负载严重不对称(如社交 Feed、报表系统)、读需要复杂投影/聚合。
**优点**:读/写各自最优;读端可水平扩展;读模型可多版本(列表视图/详情视图)。
**缺点**:最终一致(读库有投影延迟);复杂度上升一档;只适合读写分明的场景。

**不适用**:简单 CRUD(读写对称,过度工程);要求强一致读。

**落到 xdd**:architecture.md 的 API 端点清单天然分 Command(POST/PUT/DELETE)和 Query(GET)——若选 CQRS,要把两端的模型/存储分别写进规则传导矩阵。常与 [事件溯源](#13-事件溯源--event-sourcing) 组合。

---

### 13. 事件溯源 / Event Sourcing

`@quality-attr:可用性(可重放)/ 可审计性 / 可演化`

**一句话**:不存「当前状态」,只存「一系列事件」;当前状态是事件回放的结果。

**结构**:

```
[命令]─▶[领域逻辑]─▶追加事件─▶[事件存储(append-only)]
                                  │
                                  ├─▶ 投影 ─▶[读模型](快照/视图)
                                  └─▶ 回放 ─▶[重建任意时刻状态]
```

**适用**:金融/账务(需审计轨迹)、需「时间旅行」调试、需从历史重建状态的系统。
**优点**:完整审计;可重建任意时刻状态;事件是事实,天然契合领域事件。
**缺点**:事件 schema 演化难(老事件要能被新代码读);查询需投影(不能直接查);学习曲线陡。

**不适用**:状态为主、历史无所谓的(CRUD 更简单);事件量巨大且不需回溯。

**落到 xdd**:与 [事件总线](#7-事件总线--event-bus) + [CQRS](#12-cqrs命令查询职责分离) 三件套常一起。event-contract.md 的事件在此成为「事实存储」而非「消息」——语义不同,resilience 的失败模型必须覆盖「事件 schema 版本迁移」「投影重建」。

---

### 14. 六边形(端口-适配器)/ Hexagonal(整洁架构/洋葱架构变体并入)

`@quality-attr:可修改性 / 可测试性 / 安全(防腐)`

**一句话**:把领域逻辑放在核心,通过「端口」(接口)定义与外界的交互,「适配器」实现具体技术;领域不依赖任何外部。

**结构**:

```
            ┌─────────────────────────────┐
            │        领域核心(纯逻辑)      │  ← RXX 规则的家
            │   定义端口(接口),不知外部      │
            └──────────┬──────────────────┘
                       │ 端口
   ┌───────────────────┼───────────────────┐
   ▼                   ▼                   ▼
[HTTP 适配器]     [DB 适配器]         [MQ 适配器]
(HTTP/REST)      (PostgreSQL)         (Kafka)
   (适配器可替换:换 DB 只写新适配器,领域不动)
```

**变体**:整洁架构(Clean Architecture)、洋葱架构(Onion)是同一思想的不同画法——核心都是「依赖指向内,领域独立于框架/DB/UI」。本库统称「六边形」。

**适用**:核心领域复杂且需长期演进、想不被框架/DB 绑死、需要高可测试性(领域可脱离 DB 测试)。
**优点**:领域纯(无框架污染);外部可替换(换 DB/UI 不动核心);领域测试极快(不连真实依赖)。
**缺点**:概念门槛高;接口/适配器样板代码多;小项目过度工程。

**不适用**:CRUD 为主、领域薄的(分层够用);团队不熟悉依赖倒置。

**落到 xdd**:这是 [分层](#1-分层--layered) 的「严格版」——分层允许领域依赖 Infrastructure,六边形反过来要求 Infrastructure 依赖领域(依赖倒置)。architecture.md 技术栈决策若选六边形,要把「端口清单」单独列一节,每个端口标 `@intent`。

---

### 15. Space-based / 基于空间

`@quality-attr:性能(高并发突发)/ 可用性(无状态扩展)`

**一句话**:把数据/逻辑分散到内存网格的多个节点,靠内存复制+一致性哈希避免磁盘/数据库成为瓶颈;用「处理单元+数据网格+消息」组合应对峰值。

**结构**:

```
[处理单元 1]──┐                ┌──[处理单元 N]
 ├ 内存数据   │  一致性哈希/    │   ├ 内存数据
 ├ 业务逻辑   │  复制(内存网格) │   ├ 业务逻辑
 └ 备份队列   │◀──────────────▶│   └ 备份队列
        │                            │
        └──── 异步持久化(后台) ──────┘
   (无共享磁盘;请求在内存处理,绕开 DB)
```

**适用**:电商秒杀/抢购、票务高峰、超高频读写、传统 DB 撑不住的峰值场景。
**优点**:峰值抗住(内存级响应);线性扩展;DB 不在热路径。
**缺点**:实现极复杂(一致性/恢复/持久化);数据丢失风险(未持久化部分);成本高。

**不适用**:普通并发量(DB 够用);强一致要求;团队无分布式内存网格经验。

**落到 xdd**:罕见。若选,architecture.md 必须在 ODD「失败模型」里写「节点崩溃时未持久化数据如何恢复」——这是这个模式的命门。常配合 [事件溯源](#13-事件溯源--event-sourcing) 做持久化兜底。

---

## 反模式:何时不要选

| 信号 | 别选 | 改选 |
|------|------|------|
| 「大家都用微服务」 | 微服务 | 分层单体(先跑起来) |
| 「领域只有 CRUD」 | 六边形/事件溯源 | 分层 |
| 「读写在同一事务」 | CQRS | 分层 |
| 「团队 < 5 人」 | 微服务 | 分层单体 |
| 「规则一年没变过」 | 解释器/规则引擎 | 直接写代码 |
| 「要强一致线性读」 | Primary-Replica | 单库 + 分层 |

**元规则**:架构复杂度应与「问题复杂度 + 团队能力」匹配,不与「时髦度」匹配。每个复杂模式都要在 architecture.md 标 `@intent` 写清「为什么这个复杂度是值得的」。

---

## 与 xdd 三层骨架的对应

这个文件服务的是 `prompt → 设计 → 代码` 的**设计层 · 结构锚**(`xdd-architecture`)。模式选择不是孤立的,它在锚链里有明确位置:

```
intent.md(为什么)
   ↓
design.md(决策 5 段)── 其中 Alternatives 段已埋下候选模式
   ↓
spec/ RXX 规则(做什么)
   ↓
architecture.md ←【你在这里:按质量属性场景选模式】
   │  · 决策矩阵 → 候选模式
   │  · 读本文件「适用/不适用」→ 确认
   │  · 写 @intent(背景→选项→选了→为什么)
   │  · 模式决定规则传导矩阵的列(分层?管道?事件?)
   ↓
plan.md task(回指 RXX,实现所选模式的结构)
   ↓
代码 @implements RXX(按模式组织:分层就是层目录,管道就是 filter 链)
   ↓
verify 4 维一致性(architecture↔code:验证代码结构真的体现了所选模式)
```

**回溯锚**:架构模式选择写在 `architecture/{bxx-slug}/architecture.md` 的「技术栈决策」段,标 `@intent`;若下游 verify 发现「代码结构跟所选模式不符」(如选了六边形但领域层依赖了 ORM),这是 4 维一致性审计的 architecture↔code 维度的失败项,要回 architecture 改。

**变更传播**:若中途换模式(分层 → 事件驱动),沿锚链重做 architecture.md 的「规则传导矩阵」+ flow.mermaid + 事件契约,plan 的 task 全部重排。这是大改,`agents/xdd-walker.md` 的变更传播表会触发。
