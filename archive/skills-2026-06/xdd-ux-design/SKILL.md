# UX 设计思维与审查框架

## 1. 核心理念：UX = 艺术 × 科学

UX 既不是纯艺术也不是纯科学，二者缺一不可：

| 维度 | 艺术侧 | 科学侧 |
|---|---|---|
| 思考方式 | 创造力、想象力、情感共鸣 | 系统化、结构化、可验证 |
| 产出 | 美学、情感、吸引力 | 功能性、可用性、可衡量 |
| 风险 | 美但不中用 | 用但不爱用 |
| **UX 真相** | **二者融合：用艺术创造可能性，用科学验证可行性** |

> 引用原书："唯有融合艺术与科学，我们才能创造情感上引人入胜的用户体验，同时验证这些体验是否解决了目标用户的实际问题。"

**对前端的指导**：不要只追求"好看"或只追求"功能"，每个交互决策都要回答两个问题 —— *用户感受到什么？* 与 *我们怎么知道它有效？*

## 2. 设计思维六步法（前端转译版）

源自原书核心流程：共情 → 定义 → 构思 → 原型 → 测试 → 实施。前端语境下转译为：

### Step 1 · 共情 (Empathy)
- **前端动作**：写组件前，先问"谁在用、在什么场景、用完想达成什么"
- **检查项**：设计文档/PR 描述里有没有写出用户场景？有没有给目标用户画像（哪怕是简短的 persona）？

### Step 2 · 定义 (Define)
- **前端动作**：明确这个交互要解决的具体问题（一句话能讲清）
- **检查项**：组件/页面的核心目标是什么？成功标志是什么？

### Step 3 · 构思 (Ideate)
- **前端动作**：在编码前考虑 2~3 种交互方案
- **检查项**：是否考虑了替代方案？有没有被第一个想法锁死？

### Step 4 · 原型 (Prototype)
- **前端动作**：先用最简形态（线框、低保真）验证关键交互
- **检查项**：是否能拆成最小可用版本？是否先做最核心路径？

### Step 5 · 测试 (Test)
- **前端动作**：用真实用户/队友走查关键路径，收集反馈
- **检查项**：有没有用 5-second test / task completion / think-alout 验证过？

### Step 6 · 实施 (Implement)
- **前端动作**：交付到生产环境，建立可度量的成功指标
- **检查项**：上线后是否跟踪了关键指标（完成率、误操作率、停留时长）？

## 3. 前端 UX 审查框架

按优先级分 4 层，从最关键（破坏可用性）到最精致（情感化）：

### 🔴 L1 · 功能性（不通过则不可用）

| 检查点 | 失败信号 | 修复建议 |
|---|---|---|
| 任务可完成性 | 用户不知道点哪里能完成主任务 | CTA 必须视觉显著、文字明确 |
| 错误反馈 | 操作失败无提示 / 提示不明确 | 所有失败路径必须有可读的错误信息与下一步指引 |
| 状态可见 | 不知道当前在加载/成功/失败 | 用 loading / success / error 三态明确反馈 |
| 防破坏性操作 | 删除/清空等操作无确认 | 必须二次确认，且默认焦点在"取消" |
| 键盘可达 | 鼠标可用键盘不可用 | 所有交互元素必须 Tab 可达，Enter/Space 可触发 |

### 🟡 L2 · 可用性（不通过则难用）

| 检查点 | 检查方法 | 修复建议 |
|---|---|---|
| 一致性 | 相似功能是否用相似交互模式 | 建立组件库，统一按钮、表单、弹窗的行为 |
| 信息层次 | 第一眼能否看出谁最重要 | 用大小、颜色、间距建立 3 层视觉层次 |
| 认知负荷 | 单屏元素是否过多 | 用格式塔原则分组（接近、相似、封闭） |
| 反馈即时性 | 操作后多久能感知到变化 | < 100ms 感知瞬时；> 1s 必须有 loading |
| 撤销与返回 | 误操作能否挽回 | 提供撤销 (Undo)、返回 (Back)、退出 (Exit) |
| 移动端可用 | 触控目标是否够大 | 最小 44×44px；间距避免误触 |
| 文案清晰度 | 文案是否有歧义 | 用动词开头、避免术语、说明结果而非过程 |

### 🟢 L3 · 可达性 a11y（不通过则排他）

| 检查点 | 标准 |
|---|---|
| 语义化标签 | 按钮用 `<button>`、链接用 `<a>`、标题层级正确 |
| ARIA 属性 | 图标按钮有 `aria-label`、动态区域用 `aria-live` |
| 颜色对比度 | 文字与背景对比 ≥ 4.5:1（大字 3:1） |
| 焦点可见 | 键盘聚焦时有清晰可见的 outline（不要 `outline: none`） |
| 替代文本 | 图片有 `alt`，装饰图 `alt=""` |
| 表单可访问 | label 与 input 关联（`<label for>` 或包裹） |
| 减少动效 | 尊重 `prefers-reduced-motion` |

### 🔵 L4 · 体验质感（情感层）

| 检查点 | 描述 |
|---|---|
| 微交互 | hover/active/disabled 是否有反馈 |
| 动效合理性 | 动效是否帮助理解，而非炫技 |
| 空状态 | 没有数据时是否有友好的引导（而非空白） |
| 加载体验 | skeleton screen 还是转圈？是否给出预期时间 |
| 成功庆祝 | 完成重要任务是否有正向反馈（toast、动画） |
| 品牌一致性 | 配色、字体、语气是否统一 |

## 4. 常见 UX 反模式（必须规避）

来自前端实战的高频问题：

1. **鬼按钮**：按钮看着像文字或链接，或反之
2. **无限滚动没有尽头**：用户不知道自己在哪里、要多久
3. **模态套模态**：多层弹窗嵌套，用户迷失
4. **占位符代替标签**：输入框只用 placeholder，没有 label（聚焦即消失）
5. **错误信息只说"失败"**：不说为什么、怎么办
6. **加载态消失但内容未到**：瞬间空白闪烁
7. **响应式只断大屏**：平板/折叠屏体验崩坏
8. **图标无标签**：纯图标按钮没有文字说明或 aria-label
9. **必填项没标记**：表单提交后才报错，而不是进入时就知道
10. **暗模式只是反色**：对比度与色相未调整，伤眼

## 5. 设计反馈方法（如何给予 + 接收反馈）

源自原书第 8 章，前端走查场景实操：

### 给予反馈（走查者）
1. **先肯定后建议**：先指出做得好的部分（强化优势）
2. **具体而非主观**：不说"不好看"，说"主操作与次操作视觉权重太接近，用户不知道点哪个"
3. **对事不对人**：评论设计而非评论人
4. **提供选项**：建议 2 种以上的替代方案，而非只指问题
5. **分级严重性**：用 L1/L2/L3/L4 标识（功能性 > 可用性 > a11y > 质感）

### 接收反馈（被走查者）
1. **先听完再回应**：不打断、不立即辩解
2. **问澄清问题**："你说的'奇怪'具体是哪个瞬间？"
3. **区分观点与事实**：用户偏好 vs 用户行为数据
4. **记录而非反驳**：所有反馈都先记下来，事后筛选
5. **感谢并闭环**：改完后反馈给对方

## 6. 使用方式

### 触发场景
- 用户："帮我审查这个组件的 UX"
- 用户："这个交互设计得怎么样"
- 用户："按 UX 最佳实践改一下"
- 用户："做 design review"
- 用户："为什么这个按钮用户总点错"

### 审查模板
当被要求做 UX 审查时，按以下顺序输出：

```
## UX 审查报告 · [组件/页面名]

### 📋 上下文
- 用户场景：...
- 核心目标：...

### 🔴 L1 功能性问题（必须修）
- [问题 + 位置 + 修复建议]

### 🟡 L2 可用性问题（应该修）
- ...

### 🟢 L3 可达性问题（应该修）
- ...

### 🔵 L4 体验质感（建议修）
- ...

### ✨ 亮点
- 做得好的部分

### 📊 总体评级
- 可用 / 可改进 / 不可用
```

### 主动应用
设计组件时，主动问自己：
1. 用户的核心任务是什么？能否 3 秒内完成？
2. 失败/异常路径都有兜底吗？
3. 键盘用户能用吗？
4. 视觉层次够清晰吗？
5. 与现有设计系统一致吗？

## 7. 一句话心法

> **好的 UX 不是一个好看的界面，而是一个让用户忘记界面存在的体验。**
> —— 用户达成目标时，不应该赞叹"这个设计真好"，而应该直接达成目标离开。

设计思维提醒：先共情（理解用户）、再定义（说清问题）、后构思（多方案）、快原型（最小化）、严测试（验证）、稳实施（可衡量）。
