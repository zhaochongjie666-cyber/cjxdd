# 架构批判清单（7 维度）

> polish Step 1 的深度框架。每个维度给「好/坏信号 + 质询问题 + 反模式」。**默认怀疑，穷举 ≥3 攻击点/维度**。
> 判据源头：`design.md`（意图/决策）、`spec/{bxx}/rules.md`（RXX）、`architecture/{bxx}/architecture.md`（13 节）。

## 维度 1 · 方案合理性

**质询**：分层/限界上下文切得对吗？

| 好信号 | 坏信号（攻击点） |
|--------|----------------|
| 限界上下文边界 = 业务线边界（BXX 对齐） | 一个上下文干多业务线的事（职责泄漏） |
| 分层清晰：接口层不碰 DB，领域层不碰 HTTP | 业务逻辑漏进 controller / route handler |
| 依赖单向（外→内），无环 | 模块循环依赖（A→B→A） |

**质询问题**：
- 限界上下文之间有没有隐式耦合（共享 mutable 全局态、直接 import 对方的内部类）？
- 领域逻辑有没有泄漏到框架层（FastAPI decorator 里写业务规则）？
- 有没有「上帝类 / 上帝服务」一个类管 N 个不相关功能？

## 维度 2 · API 粒度

**质询**：端点太粗还是太细？

| 好信号 | 坏信号 |
|--------|--------|
| 一个端点 = 一个用户动作（动词明确） | 一个端点干 CRUD + 业务逻辑（太粗，POST /api/everything） |
| 完成一个用户动作调用 ≤2 个端点 | 5 个端点才能完成一个用户动作（太细，chatty） |
| RESTful 资源建模 或 显式 RPC（二选一，不混） | 同一项目 REST + RPC + GraphQL 三套混用 |

**质询问题**：
- 端点粒度跟 RXX 对得上吗？（一条 RXX 对应几个端点？一个端点对应几条 RXX？）
- 有没有「凑数端点」实际没人调？
- 批量操作有没有批量端点，还是前端循环单条调？
- 端点返回有没有过度聚合（一次返回整个对象图）或欠聚合（要 N+1 查询）？

## 维度 3 · 技术栈选型

**质询**：每个 `@intent` 选型站得住吗？

| 好信号 | 坏信号 |
|--------|--------|
| 选型跟项目规模匹配（小项目用 SQLite + 单体） | 轻量项目上 Kafka / Kubernetes / 微服务（过度工程） |
| 每个选型有 `@intent` 背景说明 | 选型没理由，「大家都在用」 |
| 选了最简的能解决问题的方案 | 选了最新最炫的（resume-driven） |

**质询问题**：
- 数据库选型跟读写特征匹配吗？（强关系却选 NoSQL / 纯 KV 却选 SQL）
- 消息队列跟吞吐匹配吗？（<100 msg/s 别上 Kafka）
- 缓存有必要吗？（读多写少才值得，别给每个查询都加缓存）
- 前端框架跟复杂度匹配吗？（静态页别上 SPA 全家桶）
- **有没有更简的替代**？（这是核心攻击点——每个重型组件都要答「为什么不用更简的」）

## 维度 4 · 替代方案

**质询**：核心决策列了 2+ 替代并说明为何不选？

| 好信号 | 坏信号 |
|--------|--------|
| design.md 每个决策项列了「选项 A/B/C → 选了 X → 为何不选 B/C」 | 只写「选 X」，没列替代 |
| 替代的否决理由具体（性能/复杂度/团队熟悉度） | 替代否决理由空泛（「B 不好」） |

**质询问题**：
- design.md 的决策项有没有「拍脑袋」嫌疑（没列替代 = 没真正比较过）？
- 否决替代的理由站得住吗？（「不熟」是合法理由，但要标明是团队约束不是技术优劣）
- 有没有该重新评估的决策（环境变了，当初的选型前提不再成立）？

## 维度 5 · 可部署可运维

**质询**：docker-compose / ODD 运维视图真能落地？

| 好信号 | 坏信号 |
|--------|--------|
| `docker-compose up` 一键起全栈 | 有手工步骤没脚本化（README 写「先手动建个表」） |
| 配置走环境变量 / .env | 配置硬编码 / 散落多处 |
| 运维视图有监控 + 日志 + 告警 闭环 | ODD 写了但代码没实现监控埋点 |
| 有健康检查端点 + 就绪探针 | 没健康检查，挂了不知道 |

**质询问题**：
- 部署步骤能完全自动化吗？哪步还要人手？
- 配置项有没有默认值兜底（没配也能跑）？
- 依赖的外部服务（DB/Redis/MQ）有 docker-compose 编排吗，还是「假设你已经装了」？
- 有没有不可重入的部署步骤（跑两次会出错）？
- 回滚预案有吗？`docker-compose down` 数据还在吗？

## 维度 6 · 事件契约

**质询**：事件驱动是否必要？同步会不会更简单？

| 好信号 | 坏信号 |
|--------|--------|
| 异步才用事件（长耗时 / 解耦 / 多消费者） | 同步能解决却上事件（增加复杂度无收益） |
| 事件契约有 schema + 版本 | 事件没 schema，消费者靠猜字段 |
| 事件幂等 + 有补偿 | 事件丢了 / 重复了没处理 |
| producer → queue → consumer 链路完整 | producer 发了但没 consumer，或 consumer 没接 |

**质询问题**：
- 这个事件驱动换成同步调用，行不行？（能行就是过度设计）
- 事件的消费者真的存在吗？（「未来可能要用」≠ 现在需要）
- 事件 payload 够消费者用吗？还是要反查 producer？
- 事件失败/重复的兜底在哪？（resilience 的 FMEA 有没有覆盖）

## 维度 7 · 数据模型

**质询**：聚合边界合理？大事务 / 跨聚合一致性问题？

| 好信号 | 坏信号 |
|--------|--------|
| 聚合边界清晰，跨聚合用 ID 引用不直接持有对象 | 聚合间直接对象引用（加载一个拉出整个对象图） |
| 一致性边界 = 事务边界（一个聚合一个事务） | 大事务跨多个聚合（长事务 / 锁竞争） |
| 跨聚合一致性用最终一致 + saga/补偿 | 跨聚合用分布式事务（2PC，重且脆） |

**质询问题**：
- 聚合边界跟业务不变量对齐吗？（该一起变的拆开了 = 一致性洞）
- 有没有「贫血模型」（实体只有 getter/setter，逻辑全在 service）？
- 关联关系有没有过深（A→B→C→D 链，N+1 查询风险）？
- 历史数据 / 软删除策略统一吗？（有的表软删有的硬删）

## 攻击点定级

- **P0** = 架构级硬伤（不改 = 交付即返工 / 上线即故障）。例：循环依赖、事务边界跨核心聚合、部署不能自动化。
- **P1** = 设计缺陷（不改 = 影响质量 / 可维护性）。例：API 过度聚合、事件没 schema、贫血模型。
- **P2** = 改进建议（锦上添花）。例：缺监控埋点、缺替代方案说明。

每条攻击点三件套：**为什么是问题 + 证据（行号）+ 怎么改（指向 xdd-architecture / xdd-spec / xdd-resilience）**。
