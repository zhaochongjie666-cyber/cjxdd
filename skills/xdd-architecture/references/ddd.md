# DDD 方法论 — 领域驱动设计

> xdd 的 DDD 方法论参考库。framework 已经在产 DDD 产物(`aggregate-landscape.md` / `event-contract.md` / `_landscape.md` 业务线=限界上下文),但缺「**怎么识别上下文边界、聚合怎么划分、通用语言怎么建**」的方法论。本文件补上这块。
>
> 服务于三层:**understand**(通用语言起点)→ **spec**(限界上下文)→ **architecture**(聚合/事件)。

## 为什么要 DDD

数据平台 / 仿真平台 / 数据管理 / 自动驾驶这类场景的共性:**领域本身复杂**(业务规则多、术语密集、边界模糊),不是技术难度大。DDD 的价值就是**把领域复杂度驯服成清晰结构**——让代码组织反映领域结构,而不是反映数据库表或 HTTP 端点。

不学 DDD 的典型症状(在仿真/数据平台里常见):
- "任务""作业""流水线""流程"四个词指同一个东西,代码里四处定义 → **通用语言缺失**
- 标注、训练、评测、回灌的代码互相 import,改一处动全身 → **限界上下文边界错**
- 一个"数据集"对象管着文件、版本、权限、标注、血缘,几千行 → **聚合划分过大**
- 自动驾驶场景库里,"场景""用例""测试""片段"混在一个 service → **领域概念没厘清**

## 核心思想:通用语言 + 模型驱动

DDD 两条腿:

1. **通用语言 (Ubiquitous Language)** —— 开发和业务**用同一套词**。代码里的类名/方法名 = 业务专家嘴里说的词。不翻译、不同义词化。这是 DDD 最核心、最被低估的一点。

   > 仿真平台例子:业务说"提交一个仿真任务",代码里就该有 `SimulationTask.submit()`,不是 `JobManager.create()` 也不是 `PipelineService.run()`。如果团队里"任务""作业""Job"三个词混用,先统一成一个,否则业务和技术永远对不上。

2. **模型驱动** —— 领域模型是核心,数据库/UI/消息队列都是模型的**实现细节**,不是设计的起点。先画领域模型,再想用什么 DB 存。

**通用语言不是术语表**——它是**活的**,随对领域理解加深而演进。每发现一个新业务概念,就是通用语言扩一个词。

## 战略设计:管边界

解决「大泥球」——把大系统切成若干**高内聚、低耦合**的限界上下文,每个上下文内部一套通用语言。

### 子域 Subdomain:核心 / 支撑 / 通用

动手切上下文前,先把整个业务领域分成三类子域。**这决定投入分配和是否值得做 DDD**:

| 类型 | 特征 | 对策 | 仿真/数据平台举例 |
|------|------|------|------------------|
| **核心子域** (Core) | 业务差异化、核心竞争力、最复杂 | **重点投入 DDD**,自己建模型 | 自动驾驶的**场景生成算法**、仿真平台的**物理仿真引擎** |
| **支撑子域** (Supporting) | 必要但非差异化,可定制 | 自己做但简化,够用即可 | 数据平台的**血缘追踪**、仿真的**任务调度** |
| **通用子域** (Generic) | 行业通用、买/开源就有 | **买现成**,别自己造轮子 | **认证授权**、**文件存储**、**通知**、**审计日志** |

**关键决策**:只有核心子域值得投入完整 DDD 建模。通用子域硬上 DDD 是浪费——认证用现成方案就够,别给 JWT 设计聚合根。

> 错误信号:给每个业务模块都画限界上下文 + 聚合。该买的没买,该简化的过度设计。

### 限界上下文 Bounded Context:切边界

**限界上下文 = 一个清晰的边界,边界内一套通用语言、一个领域模型,不与其他上下文混淆。**

同一个词在不同上下文里可以有不同含义——这正是边界存在的理由:

```
"任务(Task)" 在不同上下文的含义:
  · 仿真上下文  → 一次仿真运行请求(含场景+参数+车辆模型)
  · 标注上下文  → 一批待标注的数据帧分派
  · 训练上下文  → 一次模型训练作业(含数据集+超参)

  → 三个上下文各有自己的 Task 模型,不共享一个 Task 类
```

**怎么识别边界**(启发式,非算法):

1. **语言边界** —— 词义变了,就换个上下文。"场景"在仿真库里指"一组测试条件",在数据标注里指"标注作业的上下文环境"——这是两个上下文。
2. **团队边界** —— 不同团队负责的模块,通常对应不同上下文(康威定律)。
3. **变化速率** —— 一个区域需求频繁变,另一个稳定 → 分开,避免互相拖累。
4. **一致性边界** —— 需要强一致(同事务)的放一起;只需最终一致的可以分。

**边界判据测试**:能否用一句话说清这个上下文的职责,且不跟其他上下文重叠?说不清 = 边界还没厘清。

**反例(边界过小或过大)**:
- 过小:一个上下文只有 1-2 个概念 → 多半是同一上下文的子模块,合并
- 过大:"整个自动驾驶平台"一个上下文 → 内部语言必然混乱,按仿真/标注/训练/场景库拆

### 上下文映射 Context Map:画关系

切完上下文,画它们之间的关系。**这是跨团队协作契约**。DDD 定义 7 种关系:

| 关系 | 含义 | 适用 |
|------|------|------|
| **合作 Partnership** | 两上下文团队相互依赖,共同演进 | 紧密协作的两团队 |
| **共享内核 Shared Kernel** | 共享一小块模型(小心用,易成耦合点) | 强耦合且都不愿拆 |
| **客户-供应商 Customer-Supplier** | 上游(供应商)优先,下游(客户)跟随,但有协商 | API 提供方-消费方 |
| **遵奉者 Conformist** | 下游无条件遵循上游模型(上游强、下游弱) | 接入强势外部系统 |
| **防腐层 ACL (Anticorruption Layer)** | 下游建翻译层隔离上游模型污染 | **最常用**,接入遗留/外部系统 |
| **开放主机服务 OHS (Open Host Service)** | 上游对外提供标准化协议(如 REST/gRPC) | 对外开放 API |
| **发布语言 PL (Published Language)** | 标准化信息交换语言(如 OpenAPI/Protobuf) | 配合 OHS |
| **各行其道 Separate Ways** | 两上下文无任何技术连接 | 完全独立 |

**最该用:防腐层(ACL)**。接入第三方标注平台、接入现成仿真引擎、接入遗留数据湖——都要建 ACL 翻译,别让外部模型污染你的核心域。

```
[仿真上下文(核心)] ←ACL→ [第三方物理引擎]
[标注上下文(核心)]  ←ACL→ [外部标注平台 API]
[场景库上下文(核心)] ←OHS+PL→ [对外暴露给评测系统]
[认证上下文(通用)]  ←遵奉者→ [公司统一 IAM]
```

## 战术设计:管聚合内部

边界切好后,管**单个上下文内部怎么建模**。这是 DDD 战术模式,也是 `aggregate-landscape.md` 要写的核心内容。

### 实体 Entity / 值对象 Value Object

**实体**:有**唯一标识**(ID),身份不随属性变。两个 ID 相同的实体是"同一个"。

> 仿真任务 `SimulationTask(id=task-001)` 不论改多少次参数,都是 task-001。 → 实体

**值对象**:无身份,**只看属性值**。不可变。两个属性全等的值对象可互换。

> 场景坐标 `BoundingBox(x, y, w, h)`、时间窗口 `TimeRange(start, end)`、车辆动力学参数 `VehicleConfig(...)` → 值对象

**判据**:问自己「两个这样的对象所有字段都相等,是不是就是同一个?」——是 → 值对象;否(靠 ID 区分) → 实体。

**优先用值对象**。值对象不可变,天然无副作用,测起来简单。新手常把本该是值对象的东西做成实体(带 ID 的 `BoundingBox`),导致一堆无意义的 ID 管理。

### 聚合 Aggregate + 聚合根

**聚合 = 一组相关对象,作为一致性边界整体被加载/修改/持久化。**

**聚合根 = 聚合对外的唯一入口**,外部只能持有聚合根的引用,不能直接持有聚合内部对象。所有修改必须经过聚合根的方法。

```
聚合: 仿真任务 (SimulationTask = 聚合根)
  ├── 场景引用 SceneRef (值对象,外部聚合的 ID 引用)
  ├── 车辆模型 VehicleConfig (值对象)
  ├── 任务项列表 List<TaskItem> (实体,只能通过根访问)
  │     └── 每个 TaskItem 有状态机
  └── 不变量:任务总数 = TaskItem.count,状态推进满足业务规则

外部代码:
  task.addTaskItem(scene, config)   ✅ 经根的方法
  task.items[0].status = RUNNING    ❌ 绕过根,破坏不变量
```

**聚合的不变量(invariant)**:聚合存在的理由是**保护一组业务规则**。比如"任务一旦提交不能加新 item""item 状态只能 PENDING→RUNNING→DONE 不能回退"。这些规则由聚合根的方法强制。

### 领域事件 Domain Event

**领域事件 = 领域里发生过的、业务上有意义的事**。用过去时命名(`SimulationCompleted` 不 `CompleteSimulation`)。

```
聚合内:     task.complete() → 任务状态改 DONE,同时产生 SimulationCompleted 事件
跨聚合:     仿真聚合发 SimulationCompleted → 评测聚合订阅 → 触发评测
跨上下文:   仿真上下文发事件 → 标注上下文订阅(通过 ACL 翻译)
```

**事件是解耦利器**。但要警惕**事件风暴**(event storming 失控)——不是所有状态变化都该发事件。只发「其他聚合/上下文真的关心」的。

> 这正是 xdd `event-contract.md` 要管的:每个事件标 `@flow BXX-NYY` + 订阅方,不能隐式散射。

### 仓储 Repository / 领域服务 Domain Service / 工厂 Factory

| 构建块 | 职责 | 何时用 |
|--------|------|--------|
| **仓储 Repository** | 给聚合根提供「像集合一样」的存取(`findById`, `save`),封装持久化 | 每个聚合根一个仓储;**只对聚合根建仓储**,不对内部实体建 |
| **领域服务 Domain Service** | 放**不属于任何单一实体**的业务逻辑(跨实体协作) | 当一个操作自然涉及多个聚合,且不属于任何一个时 |
| **工厂 Factory** | 封装复杂对象的创建(重建聚合时保证不变量) | 聚合创建逻辑复杂、需要校验一组前置时 |

**注意**:仓储不是 DAO/数据库访问层。它返回的是**完整聚合**(领域对象),不是数据行。换 DB 不改仓储接口,只改实现——这正是[六边形架构](architecture-patterns.md#14-六边形端口适配器--hexagonal整洁架构洋葱架构变体并入)的端口。

## 聚合划分决策法

这是 DDD 战术里**最难、最易错**的一步。给一个实操决策流:

### 第 1 步:从通用语言找候选聚合

把领域里出现的名词列出来,每个都是潜在聚合根候选(仿真任务、场景、数据集、标注、模型...)。

### 第 2 步:对每个候选问 4 个问题

| 问题 | 是 | 否 |
|------|----|----|
| Q1:它需要保护某个**业务不变量**吗? | 是 → 可能是独立聚合 | 否 → 考虑做成别的聚合的内部实体或值对象 |
| Q2:它能否被**独立加载/修改/保存**,不需要连带加载别的? | 是 → 独立聚合 | 否 → 是某聚合的一部分 |
| Q3:它的生命周期跟另一个实体**强一致**(同事务)? | 是 → 合并到一个聚合 | 否 → 可拆 |
| Q4:外部是否需要**直接引用它的 ID**? | 是 → 独立聚合,用 ID 引用 | 否 → 内部实体 |

### 第 3 步:用「聚合小」原则收口

**聚合尽量小**。这是 DDD 反复强调的。大聚合 = 锁争用 + 加载开销 + 复杂度高。

> 常见错误:把「数据集」做成一个聚合,内部含所有文件+版本+权限+标注。结果每次改个文件版本,要把整个数据集聚合加载锁住。
> 正确:数据集是聚合根(管元数据 + 不变量),文件/版本是**独立聚合**,用 ID 引用回数据集。

**跨聚合引用只用 ID,不持有对象引用**。仿真任务引用场景,用 `sceneId: SceneId`(值对象),不直接持 `Scene` 对象——否则聚合边界就破了。

### 第 4 步:定一致性边界

| 一致性 | 处理 |
|--------|------|
| **强一致**(事务内必须满足的规则) | 放**同一聚合**内,聚合根方法保证 |
| **最终一致**(可短暂不一致,最终对齐) | 跨聚合,用**领域事件** + Saga/补偿 |

> "任务完成"必须强一致改 task 状态(单聚合内事务);"任务完成触发评测"是跨聚合,发事件异步处理,最终一致。

### 落到 aggregate-landscape.md

`xdd-architecture` 的 `aggregate-landscape.md` 已经要求写聚合清单。补上 DDD 维度,每聚合:

```markdown
| 聚合根 | 所属上下文 | 不变量 | 内部实体 | 值对象 | 发布事件 | 子域类型 |
|--------|----------|--------|---------|--------|---------|---------|
| SimulationTask | 仿真 | item 状态机单向推进;总数≤上限 | TaskItem | SceneRef, VehicleConfig | SimulationCompleted, SimulationFailed | 核心 |
| Scene | 场景库 | 场景参数不可变(版本化) | — | BoundingBox, Weather | ScenePublished | 核心 |
| Dataset | 数据管理 | 删除数据集级联软删版本 | DatasetVersion(独立聚合) | DataLineage | DatasetArchived | 支撑 |
```

## 反模式

| 反模式 | 症状 | 纠正 |
|--------|------|------|
| **贫血模型 Anemic Model** | 实体只有 getter/setter,业务逻辑全在 Service | 把不变量逻辑搬回聚合根方法,实体要有行为 |
| **大聚合 Giant Aggregate** | 一个聚合几千行,加载慢,锁争用 | 按一致性边界拆小,跨聚合用 ID + 事件 |
| **通用子域过度建模** | 给认证/文件存储/通知做完整 DDD | 用现成方案,精力留给核心子域 |
| **跨聚合对象引用** | 聚合 A 持有聚合 B 的对象引用 | 改成 `BId` 值对象引用,用仓储按需加载 |
| **仓储当 DAO** | 仓储返回数据行/DTO | 仓储返回完整聚合(领域对象) |
| **语言漂移** | 代码类名跟业务术语对不上 | 回 understand 统一通用语言,术语进 glossary.md |
| **事件风暴** | 所有状态变化都发领域事件 | 只发「其他聚合/上下文真的关心」的;event-contract 把关 |
| **边界过细** | 每个表一个限界上下文 | 按语言/团队/变化速率切,不是按表 |

**元规则**:DDD 是**驯服领域复杂度**的工具,不是「高级感」标签。领域简单(纯 CRUD)别上 DDD;领域复杂(规则密集、边界模糊)才值得投入,且只对**核心子域**重点投入。
