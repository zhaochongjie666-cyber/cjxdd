## 完整语法

### Feature（功能）

一个 Feature 描述一个业务功能区域。在 Shadow 体系中，一个 Feature 通常对应一条规则或一组紧密关联的规则。

```gherkin
Feature: 创建标注
  标注员可以对任务中的数据创建标注（2D框/3D框/语义标签）
```

### Scenario（场景）

一个 Scenario 描述一个具体的行为分支。**一个 Scenario 只验证一个行为分支**（正常路径 或 一个异常路径）。

```gherkin
  Scenario: 标注员创建有效 2D 框标注
    Given 任务已打开，状态为 IN_PROGRESS
    When 标注员在画面上拖拽创建矩形框并关联标签 "car"
    Then 创建标注记录，状态 EMPTY → IN_PROGRESS
      And 发布 AnnotationCreated 事件
```

### Background（背景）

多个 Scenario 共享的前置条件提取到 Background 中。

```gherkin
  Background:
    Given 标注员已登录
      And 任务已分配给当前用户
```

### Scenario Outline + Examples（场景大纲 + 示例）

同一逻辑、不同数据时使用 Scenario Outline，避免重复写多个几乎相同的 Scenario。

```gherkin
  Scenario Outline: 无效标签被拒绝
    Given 任务已打开
    When 标注员尝试关联标签 "<label>"
    Then 拒绝创建，错误码 <error_code>

    Examples:
      | label         | error_code    |
      | unknown-uuid  | INVALID_LABEL |
      | deleted-uuid  | INVALID_LABEL |
      | empty-string  | INVALID_LABEL |
```

### Data Tables（数据表）

用于传入结构化数据。

```gherkin
  Scenario: 批量导入标签
    Given 项目标签模板如下:
      | label_id | name   | type  |
      | uuid-001 | car    | BBOX  |
      | uuid-002 | person | BBOX  |
      | uuid-003 | road   | SPAN  |
    When 管理员点击"导入标签"
    Then 3 个标签导入成功
```

### Doc Strings（文档字符串）

用于大段文本内容（如错误消息模板、JSON 响应体）。

```gherkin
  Scenario: 错误响应格式验证
    When 标注员提交空标注
    Then 返回错误响应:
      """json
      {
        "code": "EMPTY_ANNOTATION",
        "message": "标注不能为空",
        "details": null
      }
      """
```

### Tags（标签）

标签用于分类、过滤和追溯。

```gherkin
  @P0 @covers-annotation-R02 @covers-B02-N07
  Feature: 创建标注
```

**Shadow 标签约定**：

| 标签 | 含义 | 示例 |
|------|------|------|
| `@P0` / `@P1` | 优先级 | `@P0` |
| `@covers-{rule-id}` | 覆盖的 spec 规则 | `@covers-annotation-R02` |
| `@covers-{node-id}` | 覆盖的流程节点 | `@covers-B02-N07` |
| `@quality-attribute` | 质量属性场景（L1.5） | `@quality-attribute` |
| `@dimension-{n}` | 覆盖矩阵维度 | `@dimension-2` |

## 格式纪律

### Given — 前置状态，不写操作

```gherkin
Given 任务已打开，状态为 IN_PROGRESS
  And 当前用户角色为 Annotator
```

### When — 只写一个动作

```gherkin
When 标注员在画面上拖拽创建矩形框并关联标签 "car"
```

**禁止**：一个 When 里写多个动作（如 `When 标注员创建框并点击保存并提交`）。

### Then — 必须断言具体值

```gherkin
Then 创建标注记录，状态 EMPTY → IN_PROGRESS
  And 发布 AnnotationCreated 事件
  And API 返回 201，响应体包含 { "id": "uuid-xxx", "status": "IN_PROGRESS" }
```

**禁止**："功能正常"、"操作成功"、"没有错误"等模糊断言。

### And / But — 补充上一个关键字

- `And` 补充同方向的条件或断言
- `But` 补充反向/异常断言

```gherkin
Then 标注创建成功
  And 标注状态为 IN_PROGRESS
  But 不发送邮件通知
```

## Shadow 体系映射

| Shadow 概念 | Gherkin 映射 | 说明 |
|-------------|-------------|------|
| 业务线 (BXX) | Feature 文件 | 一个业务线 = 一个 Feature 文件 |
| 规则 (RXX) | @covers 标签 | Scenario 用 @covers 标注覆盖的规则 |
| 流程节点 (BXX-NYY) | @covers 标签 | Scenario 用 @covers 标注覆盖的节点 |
| 旅程 (J-XX) | Scenario 来源 | Scenario 注释来源旅程编号 |
| 覆盖维度 | @dimension 标签 | 标注覆盖的矩阵维度号 |
| 前置条件 | Given | 规则的前置条件 → Given |
| 触发动作 | When | 规则的触发条件 → When |
| 预期结果 | Then | 规则的预期结果 → Then（含状态+事件+错误码） |
| 异常路径 | 单独 Scenario | 每个异常 = 一个独立 Scenario |
| 质量属性 | @quality-attribute | L1.5 质量属性场景用专用标签 |

### 各层 Gherkin 使用方式

| 层 | 用途 | 详略程度 |
|----|------|---------|
| L1 Spec | 规则的行为描述（可选增强） | 概要级：Given/When/Then 各 1 行 |
| L1 Research | 旅程步骤的行为预期（可选增强） | 概要级 |
| L1.5 Architecture | 质量属性场景、API 契约示例 | 概要级 |
| L2 E2E | 穷尽验收场景（强制） | 完整级：Feature/Background/Scenario Outline/Tags/Data Tables |
| L5 Plan | 方法行为摘要（从 L2 传导） | 精简级：单 Scenario |
| L6 Deploy | 部署验证步骤记录 | 精简级：单 Scenario |
| Reviewer | Findings 问题描述 | 精简级：单 Scenario |

## 自动驾驶数据平台示例

### 完整 Feature 示例（L2 E2E 级别）

```gherkin
@P0 @covers-annotation-R02 @covers-B02-N07
Feature: 标注员创建标注

  Background:
    Given 标注员 annotator1 已登录
      And 任务 T-001 已分配给 annotator1
      And 任务状态为 IN_PROGRESS
      And 项目标签模板包含:
        | label_id | name   | type  |
        | L-001    | car    | BBOX  |
        | L-002    | person | BBOX  |

  Scenario: 标注员创建有效 2D 框标注
    When 标注员在画面上拖拽创建矩形框 (100,200)-(300,400) 并关联标签 "car"
    Then 创建标注记录
      And 标注状态 EMPTY → IN_PROGRESS
      And 发布 AnnotationCreated 事件，载荷:
        """json
        {
          "annotation_id": "<auto-generated>",
          "task_id": "T-001",
          "annotator_id": "annotator1",
          "value_type": "BBOX",
          "label": "car"
        }
        """

  Scenario Outline: 无效标签被拒绝
    When 标注员尝试关联标签 "<label>"
    Then 拒绝创建，错误码 <error_code>
      And 不发布任何事件

    Examples:
      | label         | error_code    |
      | unknown-uuid  | INVALID_LABEL |
      | deleted-uuid  | INVALID_LABEL |

  Scenario: 标注框坐标超出画面范围
    When 标注员创建框坐标 x=1200 超出画面宽度 1000
    Then 拒绝创建，错误码 BBOX_OUT_OF_RANGE
      And 返回错误响应:
        """json
        {
          "code": "BBOX_OUT_OF_RANGE",
          "message": "标注框坐标超出画面范围",
          "details": { "max_width": 1000, "actual_x": 1200 }
        }
        """

  @dimension-5
  Scenario: 已提交任务不可再创建标注
    Given 任务状态为 SUBMITTED
    When 标注员尝试创建新标注
    Then 拒绝操作，错误码 INVALID_STATUS_TRANSITION

  @dimension-12
  Scenario: 双击保存按钮不创建重复标注
    When 标注员快速连续点击"保存标注"按钮 2 次（200ms 内）
    Then 只创建 1 条标注记录
      And 按钮在首次点击后立即 disabled
```

### 精简级示例（L1 Spec / L5 Plan 级别）

```gherkin
@P0 @covers-annotation-R03 @covers-B02-N08
Scenario: 标注员提交质检
  Given 标注非空，状态 IN_PROGRESS
  When 标注员点击"提交质检"
  Then 状态 IN_PROGRESS → SUBMITTED
    And 发布 AnnotationSubmitted + ReviewRequested
```

### 验证级示例（L6 Deploy 级别）

```gherkin
Scenario: 健康检查通过
  Given docker compose up -d --wait 已执行
  When curl http://localhost:3000/api/health
  Then HTTP 200
    And 响应体 { "status": "ok" }

Scenario: 创建标注端点可用
  Given 服务已启动
  When curl -X POST /api/annotations -d '{"task_id":"T-001","type":"BBOX"}'
  Then HTTP 201
    And 响应体包含 annotation_id
```

## 后端数据流场景

> 前端场景描述"用户在浏览器看到什么"，后端场景描述"数据从哪来、经过什么处理、到哪去、产生什么副作用"。

后端数据流场景适用于：
- **纯后端项目**：无前端，L2 验收完全基于 API 场景
- **后端 E2E**：L6 Phase 6 后端 E2E 场景验证
- **L1.5 API 契约**：API 端点的行为描述（补充静态 JSON 结构）
- **L1.5 事件契约**：跨聚合数据流的端到端描述

### 模式 1：API 端点行为场景

描述一个 API 端点的完整行为链：请求 → 校验 → 处理 → 响应 → DB 变化 → 事件发布。

**与前端场景的区别**：Given 用数据状态（不用浏览器），When 用 API 调用（不用点击），Then 断言 DB + 事件 + 响应体。

```gherkin
@api-contract @covers-annotation-R02 @covers-B02-N07
Feature: POST /api/annotations — 创建标注

  Background:
    Given 标注员 annotator1 已认证（JWT valid）
      And 任务 T-001 存在，status=IN_PROGRESS，分配给 annotator1
      And 项目标签模板包含标签 L-001 "car"

  Scenario: 正常创建 2D 框标注
    When POST /api/annotations
      """json
      { "task_id": "T-001", "values": [{ "label_id": "L-001", "type": "BBOX_2D", "bbox_2d": {"x":100,"y":200,"w":50,"h":80} }] }
      """
    Then HTTP 201
      And 响应体 { "status": "IN_PROGRESS", "values": [{ "label_id": "L-001" }] }
      And DB annotation 表新增 1 行，status=IN_PROGRESS, annotator_id=annotator1
      And 发布事件 AnnotationCreated { annotation_id: "<new>", task_id: "T-001", values_count: 1 }

  Scenario: 标签不在项目模板中
    When POST /api/annotations
      """json
      { "task_id": "T-001", "values": [{ "label_id": "unknown", "type": "BBOX_2D" }] }
      """
    Then HTTP 400, code=INVALID_LABEL
      And DB annotation 表无新增
      And 无事件发布

  Scenario: 任务不存在
    When POST /api/annotations
      """json
      { "task_id": "T-999", "values": [{ "label_id": "L-001", "type": "BBOX_2D" }] }
      """
    Then HTTP 404, code=TASK_NOT_FOUND
```

### 模式 2：聚合状态机场景

描述聚合根的合法/非法状态转换，每个转换附带事件发布断言。

```gherkin
@state-machine @aggregate-Annotation
Feature: Annotation 聚合状态机

  Scenario: EMPTY → IN_PROGRESS（添加第一个标注值）
    Given Annotation A-001 存在，status=EMPTY
    When 添加 AnnotationValue(label_id=L-001, type=BBOX_2D)
    Then status 变为 IN_PROGRESS
      And 无事件发布

  Scenario: IN_PROGRESS → SUBMITTED（提交质检）
    Given Annotation A-001 存在，status=IN_PROGRESS, values 非空
    When 调用 submit()
    Then status 变为 SUBMITTED
      And 发布 [AnnotationSubmitted, ReviewRequested]

  Scenario: SUBMITTED → APPROVED（质检通过）
    Given Annotation A-001 存在，status=SUBMITTED
    When 质检通过事件 ReviewPassed 到达
    Then status 变为 APPROVED

  Scenario: SUBMITTED → REWORK（质检驳回）
    Given Annotation A-001 存在，status=SUBMITTED
    When 质检驳回事件 ReviewRejected 到达
    Then status 变为 REWORK

  Scenario Outline: 非法状态转换被拒绝
    Given Annotation A-001 存在，status=<current>
    When 调用 <action>
    Then raise InvalidStatusTransition

    Examples:
      | current   | action          |
      | EMPTY     | submit          |
      | SUBMITTED | submit          |
      | APPROVED  | submit          |
      | APPROVED  | add_value       |
      | REWORK    | submit (空值)   |
```

### 模式 3：跨聚合事件驱动数据流

描述跨聚合的端到端数据流转：聚合 A 发布事件 → 事件传递 → 聚合 B 消费 → B 状态变更。

```gherkin
@event-flow @cross-aggregate
Feature: 标注提交流程的跨聚合数据流

  Scenario: 标注提交 → 质检创建 → 通知发送
    Given Annotation A-001 存在，status=IN_PROGRESS, annotator=annotator1
      And Review 聚合无 A-001 相关记录

    When Annotation.submit() 被调用
    Then Annotation A-001 status=SUBMITTED
      And 发布 AnnotationSubmitted { annotation_id: A-001 }
      And 发布 ReviewRequested { task_id: T-001, annotation_id: A-001 }

    When ReviewService 消费 ReviewRequested
    Then 创建 Review R-001，status=PENDING, annotation_id=A-001
      And NotificationService 发送通知给质检员

  Scenario: 质检驳回 → 标注回退 → 标注员重新编辑
    Given Annotation A-001 status=SUBMITTED
      And Review R-001 status=PENDING, reviewer=reviewer1

    When Review.reject(reason="标签不匹配")
    Then Review R-001 status=REJECTED
      And 发布 ReviewRejected { annotation_id: A-001, reason: "标签不匹配" }

    When Annotation 消费 ReviewRejected
    Then Annotation A-001 status=REWORK
      And 标注员 annotator1 可以重新编辑

    When 标注员修改后重新 submit()
    Then Annotation A-001 status=SUBMITTED
      And 发布 AnnotationSubmitted + ReviewRequested（第二次质检）
```

### 模式 4：事务边界场景

描述单聚合强一致 vs 跨聚合最终一致的事务边界。

```gherkin
@transaction-boundary
Feature: 标注创建和提交的事务边界

  Scenario: 单聚合内强一致 — 创建标注
    When POST /api/annotations with valid payload
    Then 单事务内完成:
      | 操作                       | 一致性  |
      | Annotation 记录插入         | 强一致  |
      | AnnotationValue 记录插入    | 强一致  |
      | status 更新为 IN_PROGRESS   | 强一致  |
    And 事务失败则全部回滚，DB 无残留

  Scenario: 跨聚合最终一致 — 标注提交后创建质检
    When Annotation.submit() 成功
    Then Annotation 事务内（强一致）:
      | 操作                       | 一致性  |
      | status → SUBMITTED          | 强一致  |
      | 发布 AnnotationSubmitted    | 强一致  |
    And Review 创建在独立事务中（通过事件触发，最终一致）:
      | 操作                       | 一致性    |
      | Review 记录插入              | 最终一致  |
      | 通知发送                    | 最终一致  |
    But Annotation 事务不等待 Review 创建完成
```

### 后端场景在各层的使用方式

| 层 | 使用模式 | 详略 |
|----|---------|------|
| L1 Spec | 模式 2（聚合状态机，概要级） | 每个转换 1 行 |
| L1.5 API 契约 | 模式 1（API 端点行为） | 正常+异常各 1 Scenario |
| L1.5 事件契约 | 模式 3+4（事件流+事务边界） | 每条数据流 1 Scenario |
| L2 E2E（纯后端） | 模式 1+3（API 场景替代浏览器场景） | 完整穷举 |
| L5 Plan | 模式 2（方法行为摘要，从 L1 传导） | 精简级 |
| L6 Deploy | 模式 1（API 健康检查验证） | 验证级 |
