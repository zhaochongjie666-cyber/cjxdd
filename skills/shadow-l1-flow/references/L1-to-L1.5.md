# L1→L1.5 Checker — L1 到 L1.5 架构覆盖检查

**检查:** L1.5 架构规划是否完整承接了 L1 的所有能力特征？

**触发时机:** L1.5 完成后、进 L2 前

### 检查清单

| # | 检查项 | 操作 |
|---|--------|------|
| 1 | L1 能力特征覆盖 | L1 spec 中的每种能力（API/UI/DB/外部服务/鉴权/异步），L1.5 项目类型分析表中是否有对应行？ |
| 2 | 强制映射规则应用 | L1 有该能力特征 → L1.5 文件清单是否应用了对应的 IF-THEN 规则？逐条对账 |
| 3 | 规则 ID → 文件映射 | L1 spec 每个 `<slug>-R0X` 规则 ID，在 L1.5 文件清单"对应 L1 规则"列是否有覆盖？ |
| 4 | 节点坐标传导 | L1 spec 中每个 `BXX-NYY` 节点坐标，L1.5 文件清单是否有对应文件引用？L1 conduction.md 的节点索引表中 L5 列是否可填充？ |
| 5 | 质量要求完整性 | L1.5 是否定义了错误处理/输入校验/日志/安全/性能 5 个维度的生产级要求？ |
| 6 | 启动配置规划 | L1.5 是否规划了启动方式（Docker/docker-compose/npm/Python 等）+ 环境变量 + 健康检查？ |
| 7 | wire 页面覆盖 | L1 `wire.svg` 中每个 `data-page` / `id="page-..."` 页面或视图，L1.5 `file-list.md` 是否有对应前端文件？ |
| 8 | wire 交互覆盖 | L1 wire 中每个 `data-action` / `data-target`，L1.5 `architecture.md` 是否映射到组件、API、路由、弹窗/抽屉或 store action？ |
| 9 | wire 状态覆盖 | L1 wire 中每个 `data-state`，L1.5 `quality.md` 或 `architecture.md` 是否有对应前端状态约定和测试要求？ |

### 执行方式

```text
1. 读取 L1 spec.md，提取：能力特征清单、规则 ID 全集
2. 读取 L1 wire 产物，提取：页面列表、交互动作、交互目标、状态列表
3. 读取 L1.5 `architecture.md`，提取：项目类型分析表、前端架构
4. 读取 L1.5 `file-list.md`，提取：文件清单 + "对应 L1 规则"列、前端文件清单
5. 读取 L1.5 `quality.md`，提取：质量要求与启动配置章节、前端状态约定
6. 逐能力特征对账：L1 有 → L1.5 分析表有 → `file-list.md` 有对应类型
7. 逐规则 ID 对账：R01/R02/... → `file-list.md` "对应 L1 规则"列
8. 逐节点坐标对账：BXX-NYY 全集 → L1.5 文件清单有对应文件 → conduction.md L5 列可填充
9. 逐 wire 页面对账：页面/视图 → `file-list.md` 前端文件
10. 逐 wire 交互对账：data-action/data-target → `architecture.md` 组件/API/路由/store
11. 缺失项 → FAIL
```

### 报告格式

```markdown
### L1→L1.5 Checker: <slug>

#### 能力特征覆盖

| L1 能力特征 | L1.5 分析表 | 文件清单有对应类型 | 状态 |
|:-----------|:-----------|:----------------|:----:|

#### 强制映射规则

| IF-THEN 规则 | L1 有此特征 | L1.5 文件清单应用 | 状态 |
|:------------|:-----------|:----------------|:----:|

#### 规则 ID → 文件映射

| L1 规则 ID | L1.5 文件清单覆盖 | 状态 |
|:-----------|:----------------|:----:|

**结论: PASS (全覆盖)** 或 **FAIL (X 项缺失)**
```
