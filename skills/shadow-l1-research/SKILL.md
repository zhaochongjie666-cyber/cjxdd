# Shadow·DDD+EDD+IDDD — 意图驱动 + 领域驱动 + 事件驱动调研

## 角色

帮你在动手写代码之前想清楚**为什么要做**、业务领域和事件驱动架构。IDDD + DDD + EDD 是**思考工具**，不是文档填空：

| 思考工具 | 帮你回答 |
|---------|---------|
| **意图定义（IDDD）** | 为什么做这个？成功标准是什么？需求变更时如何追溯？ |
| **用户理解** | 谁会用？怎么用？谁会误用？极端场景怎么办？ |
| 业务全景 | 有哪些业务线？业务线间如何依赖？全局事件流是什么？ |
| 统一语言 | 业务方和开发说的是一回事吗？ |
| 事件风暴 | 领域里到底发生了什么？事件之间如何流转？ |
| 限界上下文 | 边界在哪？哪个是核心？ |

**IDDD（意图驱动开发）**：在业务调研的第一步就定义项目意图。后续每条规则、每个 API 端点、每个技术选型都标注"为什么"。需求变更时，追溯到原始意图评估偏离。

**EDD（事件驱动开发）显式化**：事件风暴不只是列出事件，还要决定事件如何传递——进程内事件总线（模块化单体）还是消息队列（微服务/分布式）。这个决策影响 L1.5 Architecture 的技术栈和 L3/L5 的实现方式。

**业务全景 vs 业务线**：
- **意图定义（intent.md）**：项目级意图，所有业务线共享
- **业务全景（business-landscape.md）**：全局视角，列出所有业务线及依赖关系，架构师掌握全局的入口
- **项目流程总图（project.flow.mermaid）**：项目级唯一业务流程总图，承载所有业务线的 BXX 泳道和跨域流转
- **业务线（BXX-{slug}/）**：单条业务的详细调研，每条业务线有独立的 research.md/spec.md/wire 产物，不再维护独立 flow 文件

## 怎么做

### 0. 从 L0 笔记本收敛

**前置**：L0 发散笔记本（`.shadow/L0-research/`）已完成。

**L0 文件 → L1 提取映射**：

| L0 文件 | 提取什么 | 写入哪个 L1 产出 |
|---------|---------|-----------------|
| `01-industry-notes.md` | 行业背景、公认模式、行业基线 | intent.md §业务背景 + research.md §业务背景 |
| `02-competitor-analysis.md` | 竞品功能对比、差异化机会 | intent.md §成功标准（对标竞品） |
| `03-user-personas.md` | 6 维画像发散（原始） | intent.md §用户画像 → research.md §统一语言 |
| `04-user-journeys.md` | 5 层旅程穷举（原始） | intent.md §用户旅程 → research.md §旅程图 |
| `05-tech-research.md` | 技术路线利弊、开源项目参考 | research.md §技术选型 + §外部调研 |
| `06-events-brainstorm.md` | 事件风暴发散（原始） | research.md §事件风暴 |
| `07-external-references.md` | 外部来源链接和要点 | research.md §外部调研 §来源表 |

按上表顺序逐文件提取，确保每个 L0 文件的关键发现都被吸收到对应的 L1 产出中。

**收敛原则**：
- 从 L0 笔记中提取关键结论，丢弃中间过程
- 收敛后的产出必须精简但全面——coder 看到这些产出后不需要看 L0 笔记
- 画像合并到区分度检验不通过为止（如果 `.shadow/scale.md` 存在，按 `persona_max` 参数取上限；否则 ≤ 8 个）
- 旅程合并相似路径（≤ 画像数 × 5 条）
- 事件合并同义词
- 方案从 N 个收敛到 2 个

**收敛检查**：
1. 删掉 30% 内容后，下游（Flow/Spec/Wire/Harness）是否仍能开工？
2. L0 笔记中的关键发现是否全部被提取到 L1 产出中？
3. 有没有 L0 笔记中记录但 L1 产出中遗漏的风险或约束？

### 0.1 意图定义 — 为什么做这个？（IDDD）

**时机**：在业务全景之前，作为整个项目的第一步。

**核心问题**：
- 做这个项目的**根本原因**是什么？（不是"做什么"，而是"为什么"）
- **成功标准**是什么？如何量化？（"标注效率提升 40%"比"做一个标注平台"更精确）
- 如果需求变更，如何判断是**正常演进**还是**偏离意图**？

**产出**：`.shadow/L1-business/intent.md`

```markdown
# 项目意图定义

## 项目背景
原始需求来源、业务痛点、为什么要做这个。

## 核心意图（一句话）
用一句话描述项目的核心目的。

## 成功标准（可量化）
| 指标 | 当前值 | 目标值 | 度量方式 |
|------|--------|--------|---------|
| ... | ... | ... | ... |

## 用户画像（收敛后，如果 `.shadow/scale.md` 存在按 `persona_max` 参数取上限，否则 ≤ 8 个）

| 画像ID | 角色 | 核心区分度 | 预期路径数 |
|--------|------|-----------|-----------|
| P-01 | {角色1} | {一句话区分度} | ~8 |
| ... | ... | ... | ... |

**区分度检验**：把每个画像的核心行为列出来，如果两个画像的操作路径高度重合 → 合并。

## 用户旅程（收敛后）

| 画像 | 主线 | 分支 | 迂回 | 意外 | 探索 | 总计 | 涉及业务线 |
|------|------|------|------|------|------|------|-----------|
| P-01 | 1 | 4 | 3 | 2 | 3 | 13 | B01,B02 |
| ... | ... | ... | ... | ... | ... | ... | ... |

**旅程完成标准**：总旅程数 ≥ 画像数 × 5。每个画像至少覆盖主线+分支+意外各 1 条。

## 意图约束（不可妥协的底线）
- ...

## 变更追溯基准
1. 原始意图是什么？（来自本文档）
2. 变更是正常演进还是偏离？
3. 偏离的话，是否需要重新评估项目方向？
```

**传导方式**：
- `intent.md` → spec.md 每条规则标注 `@intent`
- `intent.md` → architecture.md 技术选型标注 `@intent`
- `intent.md` → plan.json 每个任务标注 `intent`
- `intent.md 用户画像` → L1 Flow/Spec/Wire → L2 E2E → L5 Harness
- 需求变更时追溯 `intent.md` 评估偏离

### 0.2 旅程图格式（收敛后）

从 L0 笔记中收敛的关键旅程，使用业务场景语言记录：

```markdown
## 旅程图：P-XX → <目标> [J-L1-XX]

| 属性 | 值 |
|------|-----|
| 画像 | P-XX: <名称> |
| 旅程类型 | 主线/分支/迂回/意外/探索 |
| 触发条件 | <什么情况下会走这条路径> |
| 涉及业务线 | <BXX 列表> |

| 步骤 | 用户操作（业务场景语言） | 用户看到的场景 | 可能分支 |
|------|----------------------|-------------|---------|
| 1 | ... | ... | ... |
```

旅程图要求：用户操作用业务动作描述（不写 URL/组件/技术术语）；场景用自然语言描述；相同界面使用相同场景名称；粒度精确到"一个页面/弹窗/抽屉/状态变体"；可能分支包括成功和失败路径。

**详细用户画像发散方法 + 情绪描写技巧见 [references/persona-detail.md](references/persona-detail.md)**

### 1. 业务全景 — 架构师的全局视图

**时机**：在开始各业务线详细调研前，先画出业务全景。

**产出**：`.shadow/L1-business/business-landscape.md`

#### 1.1 业务线清单

列出所有业务线，每条业务线标注：

| 维度 | 说明 |
|------|------|
| **业务线编号** | B01, B02, B03... |
| **slug** | 业务线英文名，小写连字符。一旦确定，全链路不可变。用作目录名、规则 ID 前缀、文件路径 |
| **业务线名称** | 采集打点、用户管理、标注... |
| **核心流程** | 一句话描述主流程 |
| **域类型** | Core（核心）/ Supporting（支撑）/ Generic（通用） |
| **依赖** | 依赖哪些其他业务线？被哪些业务线依赖？ |

**slug 规则**：
- 格式：小写英文字母 + 连字符，如 `collection`、`annotation`、`simulation`
- 来自业务线的核心域名词，简短且唯一
- 确定后不可修改——下游 Flow、Spec、Wire、L1.5、L5 Plan、L5 Impl、L6 全部依赖此值

#### 1.2 业务线间依赖关系

画出业务线间的依赖方向，标注依赖类型：
- **强依赖**：没有上游业务线，下游业务线无法运行
- **弱依赖**：下游业务线可以独立运行，但需要上游数据
- **双向依赖**：两个业务线互相依赖（需要警惕，可能边界划分不清）

#### 1.3 全局事件流

画出跨业务线的领域事件流转。标注每个事件属于哪个业务线，事件如何跨业务线传递。

#### 1.4 核心/支撑/通用域划分

| 类型 | 说明 | 开发策略 |
|------|------|---------|
| **Core Domain** | 核心业务，差异化竞争力 | 投入最多资源，自己做 |
| **Supporting** | 支撑核心业务 | 可以做，但可以简化 |
| **Generic** | 通用能力 | 外购/复用，不重复造轮子 |

**多业务线详细调研方法见 [references/multi-bizline.md](references/multi-bizline.md)**（精简目录，含核心铁律 + 3 个专题指南链接）：
- 命名与编号规范：[references/bizline-naming-guide.md](references/bizline-naming-guide.md)（BXX-NYY 编号、标识系统、泳道视觉规范）
- 跨线连接指南：[references/bizline-crossline-guide.md](references/bizline-crossline-guide.md)（跨线连接协议、5 种典型交叉场景）
- 流程总图指南：[references/bizline-flow-template.md](references/bizline-flow-template.md)（总图模板、多业务线工作流、Gate 检查扩展）

### 2. 统一语言 — 把术语对齐

列出所有核心业务术语，每个问三个问题：
- 这个词是什么意思？（定义）
- 谁会用这个词？（角色）
- 有没有容易混淆的词？（辨析）

如果不同上下文里同一个词意思不同，必须分开列。**够用就行**：术语 < 10 个也可以，不需要硬凑。

### 3. 事件风暴 — 发生了什么 + EDD 架构决策

#### 3.1 列出领域事件

用过去时态动词列出领域里发生的重要事件。每个事件问：
- 什么触发了它？（命令/操作）
- 谁干的？（角色）
- 它改变了什么？（聚合状态变化）
- 谁需要知道？（其他上下文）
- **事件接收方在同一个进程还是不同进程？**（EDD 关键问题）

**关键原则**：事件是业务关心的，不是技术关心的。不要列技术事件。

#### 3.2 事件分类（EDD 准备）

把事件按传递范围分类：

| 类型 | 范围 | 传递方式 |
|------|------|---------|
| **进程内事件** | 同一上下文内 | EventBus |
| **跨上下文事件** | 不同限界上下文间 | EventBus + 防腐层适配 |
| **跨进程事件** | 不同服务实例 | Kafka/RabbitMQ/SQS |
| **外部系统事件** | 第三方系统 | Kafka + 死信队列 + 重试 |

#### 3.3 EDD 架构决策

根据事件分类，显式选择事件传递基础设施（进程内 EventBus / 消息队列），决策写入 research.md。

**详细事件风暴方法 + EDD 架构决策详细指南见 [references/event-storming-detail.md](references/event-storming-detail.md)**

### 4. 限界上下文 — 边界在哪

划分子域：
- **Core Domain**：核心业务，差异化竞争力（自己做）
- **Supporting**：支撑核心业务（自己做但可以简化）
- **Generic**：通用能力（外购/复用）

划完后标出上下文之间的关系（上下游/共享内核/防腐层）。

**EDD 视角**：上下文间关系决定了事件传递方式——上下游关系用跨上下文事件；共享内核直接调用；防腐层需要适配器转换。

### 5. 用户理解 + 外部调研 — 不闭门造车（强制步骤）

#### 5.1 用户理解

**核心**：画像不是标签堆砌，旅程不是模板填空。每个画像去掉角色标签后仍有人物感，每条旅程读起来有心流。

从 6 个维度发散用户画像（角色与职责、技能水平、使用频率、目标与动机、操作环境、行为模式），5 个层次穷举旅程（主线、分支、迂回、意外、探索）。

收敛后画像 ≤ 8 个，旅程 ≥ 画像数 × 5 条。

**详细用户画像发散方法 + 情绪描写技巧见 [references/persona-detail.md](references/persona-detail.md)**

#### 5.2 外部调研

**时机**：统一语言、事件风暴、限界上下文完成后，方案选型之前。

**核心问题**：别人怎么做的？有没有现成的最佳实践、开源方案、社区经验可以借鉴？

必须找到**至少 3 个不同方向的参考来源**：

| 方向 | 调研目标 |
|------|---------|
| **行业最佳实践** | 该领域的公认设计模式、架构范式 |
| **开源项目参考** | GitHub 上同类型项目的架构、功能划分 |
| **社区推荐与讨论** | 技术社区、博客中的经验总结、踩坑记录 |
| **竞品/产品分析** | 市面上同类产品的功能列表、差异化 |
| **学术论文/标准** | 学术研究、行业标准中的理论框架 |

**调研方法**：Web Search → Web Fetch 获取详细内容 → 开源项目分析 → 经验提取。

**产出**（嵌入 research.md）：来源表 + 可借鉴的设计模式 + 已知陷阱与避坑 + 技术选型参考。

**外部调研直接输入方案选型**。每个候选方案必须引用至少 1 个外部来源作为佐证。没有外部调研支撑的方案选型不可接受。

### 6. 方案选型

至少考虑 2 个方案。每个方案说清楚：
- 做什么
- 技术可行性
- 成本
- 风险
- **EDD 架构适配性**（事件传递方式是否匹配）

```markdown
### 收敛丢弃清单

| 丢弃场景 | 来源画像/旅程 | 丢弃原因 | 恢复条件 |
|---------|-------------|---------|---------|
| 标注员在手机上标注 | 旅程 J19 | 当前只做 PC 端 | PM 确认移动端计划后恢复 |
```

## 约束

- **L0 发散是前置条件**：L1 Research 开始前，L0 发散笔记本应已完成
- **收敛是强制步骤**：从 L0 笔记中提取关键结论，产出精简但全面的 L1 文档
- **收敛后画像 ≤ 8 个**（合并到区分度检验不通过为止）
- **收敛后旅程 ≥ 画像数 × 5**（关键旅程）
- **旅程描述使用业务场景语言**：不涉及 URL/组件/data-page/Playwright 等技术实现细节
- **外部调研结论必须有**：来源表 + 可借鉴模式 + 已知陷阱 + 技术选型参考
- **方案选型必须引用外部来源**：每个候选方案至少引用 1 个外部来源
- 术语一旦定义，后续所有层必须保持一致使用
- 领域事件必须传导到 project.flow.mermaid 和 spec.md

## 简单项目示例：自动驾驶数据平台

项目：自动驾驶数据平台。采集外场数据+打点，标注数据+质检闭环，仿真回放+问题标记。三业务线。

### intent.md

```markdown
# 自动驾驶数据平台 — 项目意图

## 为什么做
自动驾驶算法训练需要高质量标注数据。当前采集、标注、仿真三个环节断裂，需要统一平台串联。

## 成功标准（可量化）
| 指标 | 基线 | 目标 |
|------|------|------|
| 采集效率 | 手动记录，2h/场景 | < 30min/场景 |
| 标注效率 | 人工 2h/百条 | < 30min/百条 |
| 质检驳回率 | 30% 返工 | < 10% 驳回率 |

## 用户画像（4 个）
| ID | 画像 | 核心行为 | 区分度 |
|----|------|---------|--------|
| P-01 | 采集员 | 外场驾驶采集数据，实时打点记录关键场景 | 高频写入，关注速度和准确性 |
| P-02 | 标注员 | 对采集数据进行 2D/3D 标注，提交质检 | 高频标注，关注工具效率 |
| P-03 | 质检员 | 审核标注结果，通过或驳回返工 | 审核操作，关注一致性 |
| P-04 | 仿真操作员 | 回放采集场景，标记问题帧，导出报告 | 回放+标记，关注场景覆盖 |

## 用户旅程（8 条）
| ID | 画像 | 类型 | 旅程名 | 核心步骤 |
|----|------|------|--------|---------|
| J-01 | P-01 | 主线 | 外场采集 | 创建采集任务→开始采集→实时打点→结束采集→上传数据 |
| J-02 | P-01 | 分支 | 补采 | 查看历史→发现缺失→创建补采任务→采集→上传 |
| J-03 | P-01 | 异常 | 采集中断 | 设备异常→保存已采集数据→标记异常→后续补采 |
| J-04 | P-02 | 主线 | 标注作业 | 打开任务→查看画面→创建标注→提交质检 |
| J-05 | P-03 | 主线 | 质检审核 | 打开待审任务→逐帧检查→通过/驳回 |
| J-06 | P-02 | 迂回 | 返工修改 | 收到驳回通知→查看原因→修改→重新提交 |
| J-07 | P-04 | 主线 | 仿真回放 | 选择场景→播放回放→标记问题帧→导出报告 |
| J-08 | P-04 | 分支 | 问题回溯 | 查看问题帧→定位原始采集场景→查看打点信息 |

## 意图约束
- 采集数据为视频+点云+GPS，单场景数据量 > 1GB
- 标注支持 2D 框选和 3D 点云标注
- 质检驳回必须填写原因，标注员可看到原因
- 仿真回放需要同步视频+点云+标注叠加
```

```markdown
# B02-annotation 标注 — 业务调研

## 统一语言
| 术语 | 英文 | 定义 |
|------|------|------|
| 标注任务 | AnnotationTask | 分配给标注员的一批待标注数据 |
| 标注 | Annotation | 标注员对一帧数据创建的标注结果 |
| 质检 | Review | 质检员对标注结果的审核 |
| 驳回 | Reject | 质检不通过，标注需返工 |

## 事件风暴
| 事件名 | 触发时机 | 分类 |
|--------|---------|------|
| AnnotationCreated | 标注员创建标注 | 进程内 |
| AnnotationSubmitted | 标注员提交质检 | 进程内 |
| ReviewPassed | 质检通过 | 进程内 |
| ReviewRejected | 质检驳回 | 进程内 |
| DataAvailable | 采集数据上传完成 | 跨上下文 |

EDD 决策：进程内 EventBus 处理标注内部事件；消息队列处理跨上下文事件。
```
